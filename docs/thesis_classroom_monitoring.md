## 摘要

针对传统课堂管理中异常行为发现不及时、事件记录不完整、课后复盘缺少客观依据等问题，本文设计并实现了一套课堂异常行为智能检测系统。系统围绕课堂视频数据采集、样本整理、行为类别标注、YOLO 模型训练与部署展开，采用 YOLO 与 SAHI 分片检测获取学生行为状态，并结合座位匹配、滑动窗口告警和多模态视觉模型复核，辅助识别疑似低头、疑似睡觉、疑似转头和疑似吃东西等状态。系统基于 FastAPI、Vue 和 MySQL 构建，形成“数据准备、模型检测、事件留痕、语义复核、教学复盘”的闭环流程，具有一定人工智能应用与工程实践价值。

关键词：课堂异常行为；数据标注；YOLO；计算机视觉；教学复盘

## 前言

课堂是学校教学活动的基本场所，教师在课堂中不仅要完成知识讲授，还要持续关注学生的听课状态、互动情况和课堂秩序。对于人数较多的班级，教师通常难以同时关注每个学生的姿态变化和异常行为。当学生出现长时间低头、趴桌、频繁转头、吃东西等情况时，如果教师完全依靠主观观察进行判断，容易出现遗漏、误判或记录不完整的问题。课堂管理并不应简单等同于监控学生，而应服务于教学反馈、课堂秩序维护和学生学习状态改善。因此，如何在尊重教育场景和隐私边界的前提下，利用计算机视觉技术对课堂行为进行辅助识别，具有一定研究和应用意义。

近年来，深度学习在目标检测、姿态估计和图像理解等方向取得了较快发展。YOLO 系列模型因推理速度较快、部署便利，在实时目标检测场景中应用广泛。课堂行为识别相关综述指出，基于计算机视觉的课堂行为识别主要关注身体动作、学习参与、注意力和情绪等维度，其中深度学习方法已经成为主流技术路线，YOLO 系列模型也被用于多类课堂行为识别任务[1]。但是，课堂场景具有目标密集、遮挡较多、学生距离镜头较远、画面分辨率较高、异常行为边界不清晰等特点。单纯依靠检测模型输出类别，容易将正常写字、看书、低头阅读等行为误判为异常。为降低此类误判，系统需要结合时序规则、局部截图复核和人工复盘机制，形成更加稳健的工程方案。

本文所设计的课堂异常行为智能检测系统不是以提出新的检测网络结构为目标，而是以完成一个可运行、可扩展、可复盘的软件系统为目标。系统围绕“实时发现异常、保存事件证据、支持课后复盘”三个核心问题展开设计。在检测层面，系统采用 YOLO 检测模型和 SAHI 分片推理方法，提高课堂大画面中学生目标的检测可用性。SAHI 通过切分图像并合并推理结果的方式，能够缓解小目标在高分辨率图像中占像素较少的问题[2]。在业务层面，系统通过座位编号、滑动窗口规则、告警等级、VLM 语义复核和数据库持久化，将单帧检测结果转化为可展示、可追踪、可复盘的课堂事件。在交互层面，系统为教师提供实时监控页、异常通知列表、历史监控记录和教学复盘表单，使系统结果能够进入教学管理流程。

与单纯的目标检测演示相比，本文系统的特点在于把人工智能识别结果嵌入完整教学业务链路。系统不是简单地在画面上画出检测框，而是进一步解决了四个实际问题：一是通过分片检测和座位匹配提高课堂大画面中学生目标的可用性；二是通过滑动窗口规则将偶然单帧结果转化为具有持续性的告警事件；三是通过多模态视觉模型对异常截图进行语义复核，使事件具备可读原因；四是通过历史记录和教学复盘把检测结果转化为课后分析材料。这些设计虽然不属于高难度理论创新，但体现了面向真实课堂场景的工程创新和应用价值。

本文的主要工作包括以下几个方面：第一，结合课堂异常行为管理需求，分析系统的角色权限、功能需求和非功能需求；第二，围绕课堂视频样本整理、行为类别定义和标注质量控制，设计面向 YOLO 模型训练的数据准备流程；第三，设计前后端分离的总体架构，明确视频处理、检测推理、事件生成、数据存储和前端展示之间的关系；第四，实现视频帧读取、YOLO/SAHI 检测、匈牙利座位匹配、滑动窗口告警、多模态视觉模型复核和 WebSocket 状态推送等关键模块；第五，建立包含系统权限表、教学基础数据表和监控业务表的数据库结构；第六，设计系统功能测试、模型评估和结果分析方案，说明系统当前完成度、适用范围和后续优化方向。本文的创新点主要体现在“数据集场景化、检测结果业务化、异常判断连续化、模型复核可解释化、教学复盘闭环化”五个方面。

本文结构安排如下：第一章介绍课堂异常行为检测涉及的相关技术和理论基础；第二章从应用场景、用户角色、功能需求和非功能需求等方面进行系统需求分析；第三章给出系统总体架构、业务流程、数据库结构、接口通信和部署设计；第四章详细说明数据集整理、模型训练和系统关键模块的设计与实现；第五章从功能测试、接口测试、模型评估方案、异常识别案例和系统稳定性等方面进行测试与分析；最后给出结论、总结与体会、谢辞、参考文献和附录。

# 第一章 相关技术与理论基础

## 1.1 课堂异常行为智能检测研究背景

课堂行为识别是教育信息化和计算机视觉交叉应用中的一个具体方向。传统课堂观察通常依赖教师经验或人工听课记录，这种方式能够体现教育判断，但难以形成持续、细粒度和可追溯的数据记录。随着摄像设备、边缘计算、深度学习模型和 Web 应用技术的发展，课堂视频可以成为教学过程分析的重要数据来源。相关研究表明，基于视觉线索的课堂行为计算可以捕捉教师和学生的课堂状态，为教学互动分析和学习状态反馈提供支持[1]。这说明课堂行为识别具有明确应用价值，但同时也要求系统设计者谨慎处理行为定义、误判风险和隐私保护问题。

课堂异常行为与普通目标检测任务相比有明显差异。普通目标检测通常关注物体类别和位置，例如车辆、行人、动物等；课堂异常行为识别不仅需要识别学生目标，还要判断学生姿态与课堂语境之间的关系。低头可能是异常，也可能是正常书写或阅读；身体前倾可能是趴桌，也可能是伏案记录；转头可能是交流，也可能只是短暂回头。因此，课堂异常行为检测不能只看单帧图像类别，还需要结合持续时间、发生频率、检测置信度、截图可见区域和教师复盘结果进行综合判断。

从工程实践角度看，课堂异常行为智能检测系统应定位为教师教学管理的辅助工具，而不是替代教师判断的自动处分系统。系统输出应采用“疑似”表述，避免对学生作出绝对化、人格化或评价性判断。本文系统中的多模态视觉模型提示词明确要求只能根据可见内容判断主要学生姿态，不得识别学生身份，不得推测姓名、性别、年龄、情绪、成绩和性格等个人属性，并要求所有异常结论使用“疑似”语气。这种约束体现了教育场景中技术使用的边界意识。

## 1.2 目标检测技术概述

目标检测是计算机视觉中的基础任务，目标是在图像中定位特定类别对象并输出边界框和类别信息。早期目标检测方法通常依赖人工特征和传统分类器，随着深度学习的发展，基于卷积神经网络的检测方法逐渐成为主流。YOLO 系列模型将目标检测建模为端到端的回归问题，能够在速度和精度之间取得较好平衡，因此经常被用于实时视频分析场景。YOLOv8 相关研究对其骨干网络、多尺度特征融合和 anchor-free 设计等方面进行了分析，指出该系列模型具有较好的开发便利性和部署适应性[3]。

在课堂场景中，目标检测模型需要面对多个实际困难。首先，学生在画面中分布较密集，检测框之间距离较近，容易发生遮挡和重叠。其次，后排学生在画面中目标较小，常规缩放推理可能导致姿态细节丢失。再次，课堂摄像机视角相对固定，但不同教室、不同班级、不同视频源之间的光照、角度和分辨率存在差异，模型泛化能力会影响系统稳定性。最后，异常行为类别之间存在语义相近问题，例如“低头”和“趴桌”并非完全由一个固定角度决定，还受到桌面可见性、上半身姿态和画面裁剪范围影响。

本系统将目标检测作为第一阶段识别手段，而不是最终判断的唯一来源。检测模型输出的类别被映射为 NORMAL、HEAD_DOWN、DESK_LYING、TURNING_HEAD 和 EATING 等状态码，再由滑动窗口规则判断是否生成“提示”或“警告”级别事件。这样设计的原因在于，单帧检测结果容易受遮挡、模糊和偶然姿态影响，通过连续窗口可以过滤短时波动，减少一帧误检立即触发告警的情况。

目标检测模型能否在课堂场景中稳定工作，与数据集质量直接相关。课堂行为数据集不仅需要包含不同座位区域、不同光照、不同学生姿态和不同清晰度的样本，还需要对类别边界作出统一规定。例如，正常写字和疑似低头在视觉上较为接近，标注时应结合头部朝向、上半身姿态、持续动作和桌面关系进行判断；趴桌与低头的区别也需要通过头肩位置、身体倾斜程度和桌面接触情况进行区分。因此，数据标注不是简单画框，而是把课堂管理问题转化为可训练视觉类别的关键环节。

YOLO 模型训练通常包括数据划分、标注格式转换、预训练权重加载、数据增强、训练迭代、验证集评估和模型导出等步骤。对于本文系统而言，模型训练目标不是追求复杂网络创新，而是使检测模型能够覆盖课堂异常行为的核心类别，并以 `.pt` 权重文件形式嵌入后端推理流程。模型评估应重点关注 Precision、Recall、mAP、混淆矩阵和典型误检样例，以便判断低头、趴桌、转头、吃东西等类别是否满足系统应用需要。

## 1.3 SAHI 分片检测技术

SAHI 即 Slicing Aided Hyper Inference，是一种面向小目标检测的通用切片推理方法。Akyon 等提出 SAHI 的背景是，在监控、航拍等高分辨率场景中，远距离目标在整张图像中占用像素较少，直接缩放到检测模型输入尺寸后容易丢失细节[2]。SAHI 的基本思想是将原始大图切分为若干重叠小图，对每个小图分别进行目标检测，再将各切片结果映射回原图坐标并进行后处理合并。该方法不依赖特定检测模型，可以叠加在不同检测器之上。

课堂监控画面通常是固定机位拍摄的宽幅视频，前排学生目标较大，后排学生目标较小。如果直接对整帧图像缩放到固定输入尺寸，后排学生的头肩和上半身细节可能不足，导致检测结果不稳定。采用 SAHI 分片推理后，局部画面在推理前能保留更多像素细节，有利于提高小目标可见性。本文系统在后端检测循环中通过 `get_sliced_prediction` 对当前视频帧进行切片检测，切片高度和宽度均设置为 640，并在后处理中合并检测结果。这一设计与课堂画面中目标密集、大小差异明显的特点相匹配。

SAHI 也会带来额外计算开销，因为同一帧需要被切分为多个子图分别推理。系统设计时需要在识别稳定性和实时性之间进行平衡。本文系统将检测循环设置为周期性执行，每轮检测后间隔约 2 秒，并只对达到告警条件的座位进行 VLM 复核。这样可以避免每一帧都进行高成本分析，在保证课堂事件可被记录的同时控制计算压力。

## 1.4 多模态视觉模型复核技术

多模态视觉模型能够同时处理图像和文本指令，对输入图像进行描述、问答、定位或语义判断。阿里云 Model Studio 文档说明，视觉理解模型可以基于用户提供的图像或视频回答问题，适用于图像描述、视觉问答和对象定位等任务[4]。在课堂异常行为识别场景中，传统检测模型输出的是类别和边界框，而教师更需要知道“为什么系统认为该座位异常”。因此，多模态视觉模型可以作为复核层，对局部截图进行语义解释。

本系统将 VLM 复核放在第二阶段，而不是对每个学生、每一帧都调用多模态模型。检测层首先通过 YOLO/SAHI 输出初步类别，滑动窗口规则判断是否达到告警条件，只有处于“警告”或“提示”的座位才进入 VLM 队列。VLM 接收目标学生裁剪图，并按照系统提示词输出 JSON 对象，字段包括 `status`、`label`、`confidence` 和 `reason`。其中 `status` 只能从 NORMAL、HEAD_DOWN、DESK_LYING、TURNING_HEAD、EATING、UNCERTAIN、EMPTY 中选择。这种受控输出方式便于后端解析，也便于数据库保存和前端展示。

在教育场景中，VLM 的使用必须受到边界约束。系统提示词要求模型不得识别学生身份，不得判断学生姓名、性别、年龄、情绪、成绩和性格等个人属性；如果截图模糊、目标太小或遮挡严重，应输出 UNCERTAIN，而不是猜测异常。这种约束降低了模型越界推理的风险，也使系统输出更接近教学辅助工具的定位。

## 1.5 FastAPI、Vue 与 MySQL 技术基础

FastAPI 是一个基于 Python 类型提示构建 API 的现代 Web 框架，官方文档强调其适合构建高性能 API 服务[5]。本系统后端使用 FastAPI 作为服务入口，统一提供登录鉴权、实时监控控制、视频流、WebSocket、历史会话、事件详情和教学复盘等接口。由于课堂监控涉及实时状态推送和视频流访问，后端不仅需要提供普通 REST 接口，还需要提供 WebSocket 连接和 MJPEG 视频响应。Uvicorn 是 Python ASGI 服务器，支持 HTTP/1.1 和 WebSocket，适合承载 FastAPI 应用[6]。

Vue 是用于构建用户界面的 JavaScript 框架，官方文档指出 Vue 提供声明式渲染和响应式机制，并支持组件化开发[7]。本系统前端基于 Vue 3 组织页面和组件，使用 Ant Design Vue 提供表格、按钮、表单、标签、弹窗和布局控件。实时监控页面通过 WebSocket 获取后端推送的座位状态和异常事件，通过视频流接口展示当前课堂画面，并在画面上叠加检测框和座位状态。历史记录页面用于查询监控会话，复盘页面用于查看异常事件截图和填写教学复盘。

MySQL 是常用关系型数据库系统，适合保存结构化业务数据[8]。本系统使用 MySQL 存储系统用户、角色、认证令牌、教师档案、班级、课程、教师班级权限、监控会话、座位快照、异常事件、事件帧、VLM 复核记录和教学复盘记录。后端使用 SQLAlchemy ORM 映射数据库表，SQLAlchemy 2.0 文档提供了 ORM、连接、事务和 schema 定义等能力说明[9]。通过 ORM 模型，系统可以在业务代码中以对象方式操作数据库，提高代码可维护性。

WebSocket 协议为客户端与服务器之间提供全双工通信能力，RFC 6455 对协议进行了规范[10]。课堂实时监控场景需要后端周期性向前端推送座位状态和事件列表，如果仅依赖前端轮询，可能增加请求开销并造成延迟。系统使用 WebSocket 定时广播状态数据，前端保持连接后即可接收最新监控状态。对于视频帧显示，系统使用浏览器可直接访问的 MJPEG 流接口，使教师端能够同时看到实时画面和结构化告警信息。

## 1.6 本章小结

本章介绍了课堂异常行为智能检测系统涉及的主要技术基础。课堂行为识别具有教育场景特点，不能简单等同于普通目标检测。YOLO 系列模型适合实时目标检测，SAHI 分片推理有助于改善高分辨率画面中的小目标检测问题，多模态视觉模型可为异常截图提供语义复核。FastAPI、Vue、MySQL、WebSocket 和 Docker 等技术共同支撑系统的服务端、前端、数据存储、实时通信和部署运行。上述技术为后续系统需求分析和总体设计奠定了基础。

# 第二章 系统需求分析

## 2.1 系统应用场景分析

本文系统面向普通课堂教学场景，主要服务对象是需要进行课堂状态观察、异常事件记录和课后教学复盘的教师或管理员。系统的基本使用流程为：用户登录系统后选择有权限查看或启动监控的班级；教师进入实时监控页面，启动课堂监控；系统读取对应班级的视频源，持续进行检测分析；当某个座位连续出现疑似低头、疑似睡觉、疑似转头或疑似吃东西等情况时，系统生成异常事件并保存截图；前端实时显示学生人数、警告数、提示数和异常事件列表；课堂结束后，教师可进入历史监控页面查看会话记录，并在复盘页面填写课堂专注情况、主要问题和改进计划。

该应用场景具有三个特点。第一，系统必须支持实时性。教师在课堂中需要及时看到异常提醒，而不是课后才获得静态报告。第二，系统必须保留事件证据。仅显示“某座位异常”不足以支持复盘，系统需要保存异常截图、事件时间、座位编号、检测类别和模型说明。第三，系统必须支持权限控制。不同教师只能查看或复盘自己授权班级的监控记录，管理员可以进行更高权限的系统管理。基于这些特点，系统不能只实现一个检测脚本，而需要完成从用户登录到数据复盘的闭环业务流程。

从痛点角度看，课堂异常行为检测系统需要解决的不只是“看见异常”，还包括“少误报、能解释、可追踪、能复盘”。如果系统只输出单帧检测类别，教师很难判断其可信程度；如果系统没有截图和事件记录，课后无法回看；如果系统没有权限控制，课堂数据存在泄露风险；如果系统没有复盘入口，检测结果就无法真正服务教学改进。因此，本文系统将课堂异常行为识别划分为检测、规则、复核、留痕和复盘五个环节，使每个环节都对应一个实际教学管理问题。

## 2.2 用户角色与权限需求分析

系统主要包括管理员和教师两类用户。管理员负责系统初始化、账号管理、班级数据维护和整体监控记录查看；教师负责查看自己有权限的班级、启动课堂监控、查看实时异常事件和填写教学复盘。系统数据库中通过 `sys_user`、`sys_role` 和 `sys_user_role` 保存系统账号与角色关系，通过 `edu_teacher` 保存教师档案，通过 `edu_teacher_class` 保存教师与班级、课程之间的授权关系。

权限需求主要包括以下内容。首先，用户必须登录后才能访问实时监控、视频流、WebSocket、班级列表和历史记录等接口。其次，教师只能访问自己被授权的班级，系统需要根据教师班级权限判断其是否可以查看监控、启动监控和进行复盘。再次，管理员在提交复盘时如果没有绑定教师档案，需要额外指定教师 ID，以保证复盘记录能够关联到具体教师。最后，系统应记录登录情况和认证令牌，便于追踪用户会话和处理登出、刷新令牌等操作。

从项目实现看，后端依赖模块负责解析 Bearer token 并加载当前用户上下文，教师业务路由通过 `_allowed_class_ids` 和 `_ensure_session_access` 等函数校验班级访问范围，实时监控接口也会根据班级查看或启动权限进行限制。这些设计使系统满足毕业设计中对用户管理和权限控制的基本要求。

## 2.3 实时监控功能需求

实时监控是系统的核心功能。系统需要支持教师选择班级并启动监控，后端根据班级名称或班级编码切换对应视频源，读取视频帧并执行检测分析。前端需要显示当前班级、连接状态、监控阶段、课堂视频画面、座位检测框、学生人数、警告数量、提示数量和异常行为通知。教师还应能够停止监控，使后端结束当前监控会话并保存统计信息。

具体功能需求包括：第一，系统应支持多个班级视频源配置，例如 1 班、2 班、3 班和 4 班分别对应不同测试视频。第二，系统应在启动监控时创建监控会话，记录班级、教师、课程、操作人、视频路径、画面宽高和开始时间。第三，系统应持续读取视频帧并更新前端画面。第四，系统应对每轮检测结果维护座位状态，并在前端叠加显示。第五，系统应定时向 WebSocket 客户端推送结构化状态，使前端无需频繁轮询即可获取最新数据。第六，系统停止监控时应保存结束时间、学生总数、警告数、提示数和事件总数。

## 2.4 异常行为识别与告警需求

系统需要识别的课堂状态包括正常、疑似低头、疑似睡觉、疑似转头和疑似吃东西。由于课堂姿态存在模糊边界，系统输出应采用辅助判断方式，不应对学生作出绝对评价。后端将检测类别映射为状态码，其中 0 对应 NORMAL，1 对应 HEAD_DOWN，2 对应 DESK_LYING，3 对应 TURNING_HEAD，4 对应 EATING。系统根据滑动窗口统计最近几次检测状态，当疑似睡觉达到阈值时生成“警告”，当低头、转头和吃东西等低级异常合计达到阈值时生成“提示”。

告警需求包括两个层次。第一层是检测规则层，用于将连续检测结果转化为业务事件。例如，单次低头不一定触发事件，但连续多次出现低头、转头或吃东西状态时可以生成提示；疑似睡觉风险较高，因此触发阈值较低并标记为警告。第二层是视觉模型复核层，用于对已经触发告警的局部截图进行语义说明。VLM 的输出不会直接改变告警等级，而是补充事件的中文标签和判断原因，使教师更容易理解系统判断依据。

## 2.5 历史记录与教学复盘需求

课堂监控系统的价值不仅在于实时提醒，也在于课后复盘。系统应保存每次监控会话及其异常事件，使教师能够回顾某节课的整体情况。历史记录页面需要按班级筛选监控会话，展示班级、教师、课程、课堂主题、状态、开始时间、警告数、提示数和操作入口。复盘页面需要展示会话概要、异常事件截图、事件标签和模型原因，并提供教学效果评分、课堂专注情况、主要问题和改进计划等填写项。

教学复盘需求体现了系统从“检测工具”到“教学管理工具”的转变。异常事件本身只是客观记录，教师需要结合课程内容、课堂活动和学生实际情况进行解释。例如，某段时间学生普遍低头可能是正在做题或阅读资料，也可能是课堂参与度不足。系统通过保存事件截图和时间点，为教师提供复盘依据，但最终教学判断仍应由教师完成。

## 2.6 系统非功能需求

系统非功能需求主要包括实时性、稳定性、可维护性、安全性和可部署性。实时性要求系统能够在课堂进行过程中持续更新视频和状态，不能因单个 VLM 请求阻塞整体监控。项目中通过后台线程分别处理视频帧读取、检测分析和 VLM 队列任务，避免所有逻辑集中在主请求线程。稳定性要求数据库异常或 VLM 分析异常不应直接导致实时监控中断。项目中 `_safe_persist` 对持久化操作进行异常捕获，VLM worker 也对分析异常进行日志记录。

可维护性要求系统代码按职责分层。项目将后端入口、配置、数据库、鉴权依赖、领域模型、业务路由、监控服务和视频工具分别放在不同目录，前端也按视图、组件、布局、组合式函数和样式文件组织。安全性要求系统保护登录接口、视频流、WebSocket 和实时监控控制接口，避免未授权用户访问课堂画面。可部署性要求系统能在本地和 Docker 环境中运行，项目提供了 `docker-compose.yml`，将 MySQL、后端和前端容器组合部署。

## 2.7 本章小结

本章从应用场景、用户角色、实时监控、异常识别、历史复盘和非功能需求等方面分析了系统需求。课堂异常行为智能检测系统需要完成从视频输入到异常事件输出、从实时展示到历史复盘、从检测模型到教师决策支持的完整流程。需求分析表明，系统既要具备计算机视觉处理能力，也要具备普通业务系统的权限、数据和交互能力。

# 第三章 系统总体设计

## 3.1 系统总体架构设计

系统采用前后端分离架构，整体可划分为用户访问层、部署与代理层、后端服务层、智能分析层、数据准备与文件层。用户访问层由教师或管理员浏览器和 Vue 前端组成，负责登录、监控展示、历史记录和教学复盘。部署与代理层由 Nginx 前端容器和 Docker Compose 组成，负责静态资源服务、反向代理和多容器编排。后端服务层由 FastAPI 应用、认证路由、教师业务路由、配置与数据库模块、鉴权依赖、监控服务和视频读取工具组成。智能分析层由 YOLO 模型训练与部署、SAHI 分片检测、滑动窗口规则、多模态视觉模型和 VLM 提示词组成。数据准备与文件层由课堂视频样本、标注数据、模型文件、异常截图输出目录、MySQL 数据库和初始化 SQL 组成。

系统总体数据流如下：在模型构建阶段，先从课堂视频中抽取样本帧，完成学生行为框选、类别标注、数据划分和 YOLO 训练，导出可部署的检测权重；在系统运行阶段，教师登录系统后选择班级并启动监控，前端发送启动请求到后端，后端校验 token 和班级权限后创建监控会话，视频读取线程持续获取当前帧，检测线程定期对当前帧进行 SAHI 分片检测，检测结果进入座位匹配和滑动窗口规则，达到告警条件时保存异常截图和事件记录，VLM worker 对异常截图进行复核并更新事件说明，后端通过 WebSocket 周期性推送状态给前端，教师在页面上查看实时画面和异常通知，课堂结束后进入历史页面和复盘页面查看会话并填写复盘内容。

这种架构的优点在于职责清晰。前端不参与检测推理，只负责展示和交互；后端业务服务不直接处理复杂页面逻辑，而是提供统一接口；智能分析层集中在监控服务中，便于后续替换模型或调整规则；数据层保存结构化结果，便于课后查询和统计。系统也可以根据实际部署条件进一步拆分，例如将检测服务独立为模型服务，将 VLM 队列替换为消息队列，将静态截图访问改为受控文件服务。

## 3.2 实时检测业务流程设计

实时检测流程是系统的核心业务流程。流程开始于教师点击“启动监控”。前端携带 access token、班级编码、教师 ID 和操作人信息请求后端启动接口。后端首先校验用户身份和班级启动权限，然后根据班级编码解析运行时班级名称，并切换视频源。系统创建监控会话后，将 `state["is_running"]` 设置为 True，重置检测状态、VLM 队列和告警映射。

后台帧读取线程持续从当前视频源读取最新帧，检测线程在监控运行时获取当前帧并调用 SAHI 检测。检测结果包含边界框和类别 ID。由于同一学生在连续帧中的检测框位置可能发生变化，系统通过匈牙利算法将新检测框与已有座位进行匹配，尽量保持座位编号稳定。匹配完成后，系统根据检测类别更新每个座位的滑动窗口。若连续 NORMAL 达到恢复阈值，则清除该座位告警状态；若疑似睡觉次数或其他异常次数达到阈值，则生成异常事件。

事件生成后，系统裁剪目标座位区域并保存到 `outputs/event_crops`，同时在数据库中写入 `monitor_behavior_event` 和 `monitor_event_frame`。达到告警条件的座位会进入 VLM 队列，但系统设置了送检间隔和待处理集合，避免同一座位频繁重复调用模型。VLM 返回 JSON 后，后端解析结果并更新事件标签、原因和复核记录。前端通过 WebSocket 接收状态数据，实时更新统计卡片、检测框和事件列表。

## 3.3 数据库结构设计

系统数据库可分为三组：系统权限表、教学基础数据表和监控业务表。系统权限表包括 `sys_user`、`sys_role`、`sys_user_role`、`sys_auth_token` 和 `sys_login_log`。这些表用于保存用户账号、角色、用户角色关系、认证令牌和登录日志。教学基础数据表包括 `edu_teacher`、`edu_class`、`edu_subject` 和 `edu_teacher_class`。这些表用于保存教师档案、班级、课程以及教师对班级和课程的授权关系。监控业务表包括 `monitor_session`、`monitor_session_seat`、`monitor_behavior_event`、`monitor_event_frame`、`monitor_vlm_review` 和 `monitor_teaching_review`。

`monitor_session` 是监控会话主表，用于记录一次课堂监控的开始、结束和统计信息。其字段包括会话编号、班级 ID、班级名称、教师 ID、课程 ID、操作人、视频路径、图像宽高、状态、开始时间、结束时间、学生总数、警告数、提示数、事件数以及检测、VLM 和规则配置。`monitor_session_seat` 保存一次会话中识别到的座位信息，包括运行时座位 ID、座位编号、检测框坐标、状态、检测类别、分析来源和锁定状态。`monitor_behavior_event` 保存异常事件，包括事件 UID、会话 ID、班级 ID、座位 ID、座位编号、告警等级、状态码、中文标签、原因、来源、图片地址、边界框和事件时间。

`monitor_event_frame` 保存事件截图帧，用于将异常事件与具体截图关联。`monitor_vlm_review` 保存多模态视觉模型复核结果，包括模型名称、请求图片、原始响应、解析状态、中文标签、原因、成功标记和延迟。`monitor_teaching_review` 保存教师课后复盘内容，包括教学效果评分、课堂专注情况、主要问题、改进计划和复盘时间。通过这些表，系统能够把实时视频分析结果转化为可查询、可复盘、可统计的业务数据。

## 3.4 后端接口与 WebSocket 通信设计

后端接口分为认证接口、实时监控接口和教师业务接口。认证接口用于用户登录、刷新令牌、获取当前用户信息和登出。实时监控接口用于获取班级列表、切换班级、启动监控、停止监控、获取最新帧、访问视频流和建立 WebSocket 连接。教师业务接口用于查询授权班级、课程、历史监控会话、会话详情、会话事件、事件详情以及获取和保存教学复盘。

视频流接口与普通 REST 接口不同。浏览器原生图片流请求不方便设置 Authorization Header，因此系统允许在视频流查询参数中携带 token，后端通过统一函数从 Header 或 query 中解析 token。WebSocket 连接也支持通过 query token 或请求头加载用户上下文。连接建立后，后端将客户端加入连接集合，并记录该客户端可访问的班级范围。广播状态时，如果用户不是管理员，系统会根据授权班级过滤状态数据，避免用户看到无权访问班级的监控信息。

WebSocket 推送内容包括运行状态、时间、图像宽高、当前班级、班级列表、座位数组、事件数组和统计数据。前端接收后将其映射为实时统计卡片、座位框、事件列表和页面状态标签。由于 WebSocket 只推送结构化状态，视频画面仍通过 MJPEG 接口单独获取，这种设计使状态数据和图像数据解耦，降低单个通道的处理复杂度。

## 3.5 前端页面与交互设计

前端采用 Vue 3 组件化设计，主要页面包括登录页、实时监控页、历史监控页和课堂复盘页。登录页负责账号密码输入和 token 保存。实时监控页是系统核心页面，包含顶部状态栏、主视频面板、统计卡片、异常行为通知列表和座位图弹窗。教师进入页面后可以查看 WebSocket 连接状态，点击启动监控后，系统开始展示当前视频流和检测结果。统计卡片显示学生人数、警告数量和提示数量，异常行为通知列表展示座位编号、异常标签、事件时间和截图入口。

历史监控页用于展示监控会话列表。页面支持按班级筛选，并以表格形式展示班级、教师、课程、课堂主题、状态、开始时间、警告数、提示数和复盘操作。课堂复盘页由会话概要、异常事件列表和复盘表单组成。会话概要显示班级、课程、学生数、警告数、提示数和事件数。异常事件列表展示事件截图、座位编号、异常标签和原因。复盘表单提供教学效果评分、课堂专注情况、主要问题和改进计划字段，教师填写后提交到后端保存。

前端交互设计强调教师可读性。系统没有直接展示模型原始类别 ID，而是通过中文标签呈现“疑似低头”“疑似睡觉”“疑似转头”“疑似吃东西”等状态。对于 VLM 无法判断的情况，系统可显示“无法确定”或“未看到可分析学生”。这种表达方式比直接显示模型类别更适合教学场景，也符合教育管理中谨慎判断的要求。

## 3.6 系统部署设计

系统支持本地启动和 Docker Compose 启动。本地启动时，后端需要创建 Python 虚拟环境、安装 `backend/requirements.txt` 中的依赖、设置阿里云 API Key，并运行 `python backend/main.py`。前端需要进入 `web` 目录安装依赖并执行 `npm run dev`。数据库需要创建 MySQL 数据库并导入 `db/001_init_mysql.sql`。这种方式适合开发和调试。

Docker Compose 启动方式将 MySQL、后端和前端分别放入容器。MySQL 容器负责数据库服务并自动执行初始化 SQL；后端容器挂载 `inputs`、`models` 和 `outputs` 目录，便于读取测试视频、加载检测模型和保存异常截图；前端容器通过 Nginx 提供静态资源并反向代理请求。Docker Compose 官方文档说明其用于定义和运行多容器应用[11]，与本文系统的前后端和数据库组合部署需求相符。

部署设计中需要注意敏感配置。系统通过环境变量读取 MySQL 连接信息、JWT 密钥、管理员账号、管理员密码和阿里云 API Key。`.env` 文件被 `.gitignore` 忽略，避免本地密钥误提交。生产环境中应使用足够强的 JWT 密钥和管理员密码，并避免在日志中泄露 access token。视频流 query token 虽然解决了浏览器原生请求无法设置 Header 的问题，但可能出现在访问日志中，后续可改造为短期媒体票据。

## 3.7 系统设计亮点

本文系统的设计亮点主要体现在以下几个方面。

第一，构建了从“检测”到“复盘”的业务闭环。许多课堂行为识别方案停留在模型识别或截图展示层面，而本文系统将检测结果继续转化为座位状态、告警事件、截图证据、VLM 原因说明、历史会话和教学复盘记录。这样，系统输出不只是一个模型类别，而是能够进入教师课后分析流程的教学材料。

第二，建立了面向课堂行为的“数据标注 + 模型训练 + 系统部署”链路。课堂异常行为类别具有语义模糊性，直接套用通用目标检测模型难以表达低头、趴桌、转头和吃东西等教学管理关注点。本文将课堂行为需求转化为可标注、可训练、可评估的视觉类别，使论文内容从单纯调用模型扩展为人工智能应用项目的完整流程。

第三，采用“模型检测 + 规则判定 + VLM 复核”的分层识别策略。检测模型擅长快速定位目标和初步分类，但对低头写字、看书、趴桌等相似姿态容易混淆。滑动窗口规则可以过滤短时波动，VLM 复核可以对局部截图给出自然语言原因说明。三层结合后，系统在工程上兼顾了实时性、可解释性和可调整性。

第四，面向课堂座位场景设计了稳定的座位关联机制。课堂管理关注的是“哪个座位在什么时间出现什么状态”，而不仅是画面中出现了多少个检测框。系统通过匈牙利算法维护连续帧中的座位编号，使异常事件能够关联到稳定座位编号，便于前端展示、数据库记录和课后复盘。

第五，系统在教育场景中加入了隐私和权限边界。VLM 提示词明确限制模型不得识别学生身份或推测个人属性，后端对视频流、WebSocket 和监控接口进行登录鉴权，并根据教师班级权限过滤数据。该设计使系统更符合课堂场景对数据安全和谨慎判断的要求。

第六，系统具备较好的工程落地性。项目不仅包含检测逻辑，还包含前端界面、后端接口、数据库模型、权限管理、Docker 部署和文档图表。这使系统从单点算法演示扩展为一个可运行、可演示、可维护的完整毕业设计项目。

## 3.8 本章小结

本章完成了系统总体设计。系统采用前后端分离和多层架构，将用户访问、业务服务、智能分析、数据准备、数据存储和部署环境分离。系统先通过样本整理、行为标注和 YOLO 训练形成可部署检测模型，再在运行阶段经过视频读取、分片检测、座位匹配、告警判断、截图保存、VLM 复核和 WebSocket 推送，最终在前端形成可视化结果。数据库结构覆盖权限、教学基础数据和监控业务数据，为历史查询和教学复盘提供支撑。

# 第四章 系统关键模块设计与实现

## 4.1 视频帧读取与班级视频切换模块

视频帧读取模块负责为检测线程和视频流接口提供当前课堂画面。系统通过 `MockMonitorStream` 对本地测试视频进行封装，`CLASS_VIDEOS` 字典保存不同班级与视频文件之间的映射关系，例如 1 班对应 `inputs/test.mp4`，2 班对应 `inputs/v1.mp4`。系统启动时默认加载 1 班视频，并通过 OpenCV 的 `VideoCapture` 读取视频尺寸和最新帧。OpenCV 文档提供了 `cv::VideoCapture` 用于从视频文件或摄像设备中抓取帧的接口说明[12]，本系统利用这一能力完成课堂视频源读取。

班级切换模块用于在不同课堂视频源之间切换。当用户选择新的班级并具备相应权限时，后端调用 `switch_class` 函数切换视频路径，更新当前班级、图像宽高和最新帧，并重置检测状态。重置内容包括 VLM 送检时间、待处理座位集合、检测历史窗口、连续正常计数、告警等级映射、座位列表、事件列表和统计数据。这样可以避免上一个班级的座位编号和事件状态影响新的监控会话。

视频帧读取和班级切换模块的设计重点是隔离视频源变化对检测链路的影响。检测线程不直接关心视频来自哪个文件，只从全局状态读取当前帧。前端也不直接读取本地文件，而是访问后端视频流接口。通过这种封装，后续如果将测试视频替换为摄像头、网络流或教室监控平台接口，只需调整视频流工具模块，不需要大幅修改前端页面和告警逻辑。

## 4.2 数据集整理与行为类别标注

课堂异常行为检测的基础是高质量样本。本文系统以项目测试视频和课堂监控类视频片段为主要数据来源，先通过 OpenCV 对视频进行抽帧，再对抽取图片进行筛选和标注。抽帧阶段不宜简单逐帧保留，因为连续帧之间画面差异较小，过多相似样本会导致训练集冗余。较合理的做法是按照固定时间间隔抽帧，同时人工补充保留包含遮挡、后排小目标、光照变化、不同班级视角和典型异常姿态的样本，使数据集覆盖真实课堂中常见变化。

样本筛选主要包括四类处理。第一，删除严重模糊、黑屏、画面抖动和主体不可见的图片，避免低质量样本干扰训练。第二，去除高度重复帧，减少同一姿态在训练集中占比过高的问题。第三，保留容易混淆的边界样本，例如低头写字、看书、趴桌休息、侧身交流等，因为这些样本对模型区分能力更有价值。第四，对涉及学生面部或个人信息的图片进行使用范围控制，论文展示时应进行遮挡或模糊处理，避免泄露个人隐私。

本文将课堂行为检测类别设计为五类：NORMAL、HEAD_DOWN、DESK_LYING、TURNING_HEAD 和 EATING。NORMAL 表示正常听课、书写、阅读、看黑板等不需要告警的课堂状态；HEAD_DOWN 表示头部明显朝向桌面或视线长时间偏离正常听课方向，但上身未明显趴伏；DESK_LYING 表示头部或上半身明显接近桌面，具有疑似睡觉或趴桌特征；TURNING_HEAD 表示头部明显转向侧方或后方，偏离主要教学方向；EATING 表示画面中出现手部靠近嘴部、食品包装、进食动作等可见特征。类别定义的重点是服务系统告警和教师复盘，而不是对学生作出绝对评价。

标注时采用 YOLO 目标检测常用的边界框格式。每个标注框尽量覆盖学生头肩和上半身关键区域，框过小可能丢失姿态信息，框过大则容易引入周围同学和桌椅干扰。标注文件中每一行包含类别编号、归一化中心点坐标、归一化宽度和高度，即 `class x_center y_center width height`。本文系统中的类别编号与业务状态一一对应：0 对应 NORMAL，1 对应 HEAD_DOWN，2 对应 DESK_LYING，3 对应 TURNING_HEAD，4 对应 EATING。通过这种设计，训练数据、检测模型和后端业务状态可以保持一致，降低模型部署时的映射成本。

数据集划分时应将样本分为训练集、验证集和测试集。需要注意的是，同一视频片段中相邻帧高度相似，如果随机混合划分，可能造成训练集和测试集内容过于接近，导致评估结果偏高。更稳妥的方式是按视频片段、班级或时间段进行分组划分，使测试集尽量包含模型训练阶段未见过的场景。标注完成后，还应进行二次复核，重点检查类别边界、框选范围、漏标、多标和类别不平衡问题。对于样本较少的类别，例如 EATING，可通过补充视频片段或有控制地增加数据增强来缓解类别不均衡。

## 4.3 YOLO 模型训练与检测模型构建

YOLO 模型训练的目标是让检测模型能够识别课堂画面中的学生行为状态，并输出后端可直接使用的类别和边界框。本文系统采用迁移学习思路，在通用预训练权重基础上进行课堂行为数据微调。这样做的原因是课堂样本规模通常有限，如果完全从零开始训练，不仅训练成本较高，也容易出现收敛不稳定和泛化能力不足的问题。使用预训练模型可以继承通用视觉特征，再通过课堂行为标注数据学习具体姿态类别。

训练配置主要包括输入尺寸、批量大小、训练轮次、学习率、数据增强和早停策略。考虑到系统运行时 SAHI 切片尺寸为 640，训练输入尺寸也可设置为 640，以减少训练和部署之间的尺度差异。数据增强可以使用缩放、平移、亮度变化、轻微裁剪等方式提高模型对不同画面条件的适应能力；水平翻转应结合课堂方向谨慎使用，因为翻转后可能改变学生面向讲台的空间关系。训练过程中需要观察训练损失、验证损失、Precision、Recall、mAP50 和 mAP50-95 等指标，判断模型是否出现欠拟合或过拟合。

模型评估不应只看总体 mAP，还应结合课堂业务需求分析各类别表现。NORMAL 类误判为异常会增加教师负担；DESK_LYING 漏检可能导致较明显异常未被提醒；HEAD_DOWN 与 DESK_LYING 混淆会影响告警等级；TURNING_HEAD 和 EATING 则容易受遮挡、手部区域和画面清晰度影响。因此，训练完成后应输出混淆矩阵和典型误检样例，并对低头写字、看书、趴桌、侧身交流等边界样本进行单独观察。这样既能体现模型训练工作量，也能为系统规则阈值调整提供依据。

训练完成后，模型以 `.pt` 权重文件形式保存，并在系统运行时由后端检测模块加载。项目中检测模型路径为 `models/gmn26n-behavior.pt`，后端通过 Ultralytics 模型封装完成推理，再结合 SAHI 分片检测适配高分辨率课堂画面。需要说明的是，本文并不把创新点放在重新设计 YOLO 网络结构上，而是强调数据集构建、模型训练、分片推理、规则告警和业务复盘之间的衔接。对于毕业设计而言，这种“数据准备、模型构建、系统部署、结果复盘”的链路能够更充分体现人工智能应用开发过程。

## 4.4 基于 YOLO 与 SAHI 的课堂行为检测模块

检测模块位于 `backend/services/monitor_service.py`。系统在检测分析循环中加载基于 Ultralytics 的检测模型，模型路径为 `models/gmn26n-behavior.pt`，置信度阈值设置为 0.25，输入尺寸设置为 640。每轮检测时，系统调用 SAHI 的 `get_sliced_prediction` 对当前帧进行分片预测，切片高度和宽度均为 640，并设置后处理匹配阈值。检测结果以对象预测列表形式返回，其中包含边界框坐标和类别 ID。

检测类别通过 `CATEGORY_TO_STATUS` 映射为业务状态。类别 0 表示 NORMAL，类别 1 表示 HEAD_DOWN，类别 2 表示 DESK_LYING，类别 3 表示 TURNING_HEAD，类别 4 表示 EATING。系统将这些状态作为后续滑动窗口规则的输入，而不是直接在单帧上生成事件。该设计符合课堂场景特点，因为学生短暂低头写字、看书或看试卷并不应立即被认定为异常。

检测模块的输出不仅用于事件生成，也用于前端座位框显示。每个检测框会被格式化为 `[x1, y1, x2, y2]` 坐标，并与座位编号绑定。前端视频组件根据后端返回的座位数组，在视频画面上绘制对应检测框和状态信息，使教师能够直观看到系统识别位置。通过将训练后的课堂行为检测模型与 SAHI 分片推理结合，系统能够在大画面、多学生、小目标的课堂场景中提供较稳定的初步视觉结果。

## 4.5 基于匈牙利算法的座位匹配模块

在连续视频帧中，同一学生的检测框位置会随姿态、遮挡和检测误差产生变化。如果每次检测都重新生成座位编号，前端显示和事件记录会变得混乱。因此系统需要在新检测框与已有座位之间建立匹配关系。本文系统采用匈牙利算法解决匹配问题，目标是在当前检测框集合和已有座位集合之间寻找整体代价最小的匹配方案。

系统首先计算每个检测框的中心点和宽高，并以检测框最长边的平方作为最大匹配距离阈值。然后构建代价矩阵，矩阵行表示当前检测框，列表示已有座位和虚拟新座位列。对于每个检测框和已有座位，系统计算中心点距离平方；若距离小于阈值，则将该距离作为匹配成本；若超过阈值，则保留极大值，表示不宜匹配。对于虚拟列，系统设置固定成本，使无法匹配到已有座位的检测框能够创建新座位。最后调用 SciPy 的 `linear_sum_assignment` 求解最优匹配。

匹配完成后，如果检测框匹配到已有座位，系统更新该座位的检测框和检测类别；如果匹配到虚拟列，则创建新的座位编号。座位编号格式为 `S01`、`S02` 等，前端和数据库都使用该编号展示或记录座位。该模块使同一座位在连续检测中保持相对稳定，有利于滑动窗口统计和异常事件归因。

## 4.6 基于滑动窗口的异常告警判定模块

滑动窗口告警模块用于把连续检测状态转化为业务事件。系统为每个座位维护一个长度为 5 的检测历史队列。每轮检测后，系统将该座位当前状态追加到队列中，并更新连续 NORMAL 计数。如果连续 NORMAL 次数达到 2，系统将座位状态恢复为正常，清除告警等级并清空检测历史。这样可以在学生恢复正常姿态后及时取消异常状态。

异常告警分为“警告”和“提示”两个等级。疑似睡觉被视为较高风险异常，当滑动窗口中 DESK_LYING 出现次数达到 2 时，系统生成“警告”。疑似低头、疑似转头和疑似吃东西被归为低级异常，当三类状态合计次数达到 3 时，系统生成“提示”。如果新告警等级与旧告警等级相同，系统只更新座位状态，不重复生成事件；只有等级发生变化或首次达到阈值时才调用 `append_event` 生成异常事件。

该规则设计具有工程上的可解释性。教师可以理解系统为什么触发事件，即某个座位在最近几次检测中多次出现某类疑似异常。相比直接使用单帧检测结果，滑动窗口能减少偶然误检。相比完全依赖深度模型，规则层也便于根据学校管理要求调整阈值。例如，如果学校更关注疑似睡觉，可以降低 DESK_LYING 阈值；如果更希望减少误报，可以提高低级异常触发次数。

## 4.7 基于多模态视觉模型的异常复核模块

VLM 复核模块由任务入队、模型调用、结果解析和事件更新四部分组成。系统首先筛选当前处于“警告”或“提示”的座位，再判断该座位是否已经在待处理集合中、是否满足最小送检间隔、检测框宽高比是否适合裁剪。符合条件的座位会与当前帧副本一起进入 VLM 队列。每个 VLM worker 从队列中取出任务，裁剪目标座位局部图像，将图像编码为 base64，并通过 LangChain OpenAI 兼容接口调用 `qwen-vl-max` 模型。

模型系统提示词对输出格式和判断边界进行了严格约束。VLM 必须只输出 JSON 对象，且包含 `status`、`label`、`confidence` 和 `reason` 四个字段。系统提示词还规定，如果截图中没有可分析学生，应输出 EMPTY；如果画面模糊、遮挡严重或判断依据不足，应输出 UNCERTAIN；不要把低头写字、看书、看试卷直接判定为异常；所有异常结论必须使用“疑似”语气。这样的提示词设计降低了模型随意输出的风险，使后端能够稳定解析结果。

VLM 返回结果后，系统通过 `parse_model_json` 解析 JSON，并调用 `apply_vlm_result` 更新事件。需要注意的是，VLM 复核结果主要补充事件的 label 和 reason，不改变检测规则已经生成的告警等级。这种设计避免了 VLM 单次判断直接推翻规则层状态，同时又提升了事件说明的可读性。数据库中的 `monitor_vlm_review` 会保存模型名称、请求截图、原始响应、解析结果、成功状态和延迟，为后续排查和优化提供依据。

## 4.8 监控事件持久化与历史复盘模块

事件持久化模块负责将实时检测结果保存为数据库记录和截图文件。系统生成事件时，会先根据目标座位框裁剪截图并保存到 `outputs/event_crops`，文件名包含事件标识。随后在数据库中创建 `monitor_behavior_event` 记录，字段包括事件 UID、会话 ID、班级 ID、座位 ID、座位编号、告警等级、状态、标签、原因、来源、图片 URL、图片路径、边界框坐标和事件时间。同时，系统创建 `monitor_event_frame` 记录，保存截图 URL、截图路径、座位编号、状态文本和原始 payload。

历史复盘模块通过教师业务路由提供接口。教师可以查询自己有权访问的监控会话列表，也可以进入某个会话查看详情和事件列表。事件详情接口会返回事件基本信息和关联截图帧。复盘接口支持获取和保存教学复盘记录，教师可以填写教学效果评分、课堂专注情况、主要问题和改进计划。系统通过 `monitor_teaching_review` 表保证同一教师对同一会话只有一条复盘记录。

持久化与复盘模块使系统结果具有可追溯性。实时告警如果只在页面中短暂显示，课后难以分析；保存事件后，教师可以结合截图和模型说明进行复盘。对于毕业设计而言，这一模块也体现了系统不仅有智能识别功能，还有完整业务闭环。

## 4.9 教师端实时监控前端实现

实时监控前端页面位于 `web/src/views/MonitorView.vue`。页面通过 `useWebSocket` 获取后端推送状态，通过 `useApi` 发送启动和停止监控请求。页面顶部显示系统名称、WebSocket 连接状态、监控阶段标签和启动/停止按钮。主区域左侧为视频面板，使用 `VideoPlayer` 组件加载 MJPEG 视频流，并根据后端返回的座位数组绘制检测框。右侧为统计与事件区域，使用 `StatsCard` 显示学生人数、警告数和提示数，使用 `EventList` 展示异常事件通知。

页面在启动监控时会优先传递班级编码 `X-Class-Code`，若没有班级编码则传递 URL 编码后的班级名称。用户信息中的教师 ID、操作人 ID 和操作人名称也会随请求头传给后端。这样做的原因是 HTTP Header 不适合直接传递未编码中文，系统通过 URL 编码和后端解码避免中文请求头问题。视频流 URL 会将 access token 作为 query 参数传入，以兼容浏览器图片流请求无法设置 Authorization Header 的限制。

实时监控页面还包含座位图弹窗功能。当教师点击学生人数统计卡片时，可以打开座位图弹窗查看当前座位框分布。异常事件列表中展示的状态标签来自检测或 VLM 复核结果，前端通过 `statusLabel` 将状态码映射为中文说明。整体页面强调实时可读性，使教师能够在一个界面中同时看到画面、统计和事件。

## 4.10 本章小结

本章详细说明了系统关键模块的设计与实现。视频读取模块负责提供当前课堂帧，数据集整理与标注模块负责将课堂行为需求转化为 YOLO 可学习类别，模型训练模块负责形成可部署检测权重，检测模块负责输出学生行为类别，座位匹配模块负责维护座位编号稳定，滑动窗口模块负责将连续状态转化为告警事件，VLM 模块负责补充语义复核，持久化模块负责保存事件和复盘记录，前端模块负责实时展示和交互。各模块之间通过明确的数据结构连接，形成完整的课堂异常行为智能检测流程。

从实现效果看，本文系统的亮点不在于单个模块复杂，而在于多个模块之间形成了较完整的协同关系。数据集整理和标注解决模型“学什么”的问题，YOLO 训练解决课堂行为初步识别的问题，SAHI 解决大画面中学生目标较小的问题，匈牙利匹配解决连续帧座位编号不稳定的问题，滑动窗口解决单帧误检容易触发告警的问题，VLM 复核解决检测结果缺少解释的问题，数据库和复盘页面解决课堂事件无法沉淀的问题。这种面向问题链条的模块组合，是本文系统区别于普通检测 Demo 的主要价值。

## 5.3 接口与权限测试

接口与权限测试的重点是验证系统不会向未授权用户开放课堂视频和监控数据。系统应检查以下情况：未带 token 访问 `/api/classes`、`/api/latest_frame`、`/api/start`、`/api/stop`、`/api/switch_class` 和 `/video_feed` 时，应返回 401；教师访问未授权班级时，应返回 403；教师查看无权访问的历史会话时，应拒绝访问；管理员进行复盘提交时若没有教师档案，应要求提供教师 ID。

权限测试还需要验证 WebSocket 场景。WebSocket 连接建立时，后端会尝试从 query 参数或 Authorization Header 中解析 token，并加载用户上下文。如果没有 token 或 token 无效，连接不应获得完整监控数据。对于普通教师，后端广播状态时需要根据授权班级过滤数据；如果当前运行班级不在教师授权范围内，前端应接收到空座位、空事件和不可运行状态。这样可以避免一个教师看到其他班级的实时课堂画面。

接口与权限测试是本系统的重要质量保证。课堂视频和学生行为记录属于敏感教学数据，如果接口缺少鉴权，即使检测功能可用，也不适合实际使用。本文系统通过统一 token 解析、用户上下文加载、班级权限查询和会话访问校验，实现了基本安全控制。后续如果进入真实环境，还应进一步增加 HTTPS、访问日志脱敏、媒体短期票据和更细粒度的审计功能。

## 5.4 模型训练与检测效果评估方案

主要评价指标包括 Precision、Recall、mAP50、mAP50-95、混淆矩阵和平均推理耗时。Precision 反映模型预测为某类异常时有多少是真实异常，指标过低会导致误报增加；Recall 反映真实异常中有多少能被模型发现，指标过低会导致漏报；mAP50 和 mAP50-95 用于综合衡量边界框定位和类别判断效果；混淆矩阵用于观察 HEAD_DOWN 与 DESK_LYING、NORMAL 与 HEAD_DOWN 等相近类别之间的混淆情况；平均推理耗时用于评估模型能否满足系统实时性要求。

系统在线评估建议设置三组对比。第一组比较整图 YOLO 推理与 YOLO + SAHI 分片推理，观察后排小目标和遮挡区域的检测变化。第二组比较单帧告警与滑动窗口告警，观察误报数量是否减少。第三组比较只有检测结果和加入 VLM 复核后的事件可读性，观察教师是否更容易理解异常原因。上述对比不需要证明算法达到前沿水平，但能够说明本文系统围绕课堂痛点进行了针对性设计。

检测结果展示可选择典型截图进行分析。论文中建议放入正常听课、疑似低头、疑似趴桌、疑似转头和疑似吃东西各一张预测图，并在图下说明检测框、类别、置信度、座位编号和系统告警等级。若使用真实课堂截图，应进行人脸遮挡或局部模糊；若使用公开或测试素材，应说明素材来源和用途。通过“训练指标表 + 混淆矩阵 + 典型案例图 + 在线事件记录”的组合，可以使测试章节更符合计算机视觉应用论文的写法。

## 5.5 异常识别案例分析

异常识别案例分析应结合实际测试视频截图进行。由于本文初稿不直接嵌入真实截图，以下给出可用于最终论文的案例分析写法。第一类为疑似低头。学生头部明显朝向桌面方向，但上身未明显趴伏，系统可识别为 HEAD_DOWN。如果画面显示学生正在写字或阅读，VLM 提示词要求优先判为 NORMAL 或 UNCERTAIN，避免将正常学习动作直接判为异常。第二类为疑似睡觉。学生头部接近桌面，上身明显伏在桌面上，滑动窗口中 DESK_LYING 多次出现时，系统生成“警告”事件。第三类为疑似转头。学生头部明显转向侧方或后方，并与正常听课方向不一致，连续出现后系统生成“提示”。第四类为疑似吃东西。画面可见手部靠近嘴部、嘴部动作或桌面存在食品包装时，系统可标记为 EATING。

案例分析时应注意两个原则。第一，系统输出应使用“疑似”语气。课堂行为存在语境差异，系统不应把检测结果写成“学生睡觉”“学生违纪”之类绝对判断。第二，截图分析应避免身份识别。论文中如果使用真实学生截图，应进行遮挡或模糊处理；如果使用测试视频素材，也应说明数据来源和使用范围。对于毕业设计答辩，建议使用项目测试视频生成截图，展示系统如何从检测框、告警等级、事件截图和 VLM 原因说明形成完整记录。

## 5.6 系统实时性与稳定性分析

系统实时性主要受检测模型推理、SAHI 切片数量、VLM 调用延迟、数据库写入和 WebSocket 推送间隔影响。项目中检测分析循环每轮执行后会间隔约 2 秒，WebSocket 广播间隔为 1 秒，视频帧读取线程约每 0.04 秒更新一次最新帧。这样的设计使视频显示和结构化状态推送分离，教师端可以持续看到视频流，同时以秒级频率接收检测统计和事件变化。

SAHI 分片推理会增加检测成本，但有助于改善高分辨率课堂画面中的小目标检测。VLM 调用成本更高，因此系统只对已经达到告警条件的座位进行复核，并设置 10 秒送检间隔和最大队列长度。队列满时系统会丢弃部分 VLM 任务，避免后续帧一直积压。这种策略体现了实时系统中的降级思想：当外部模型处理能力不足时，系统优先保证主监控链路继续运行。

稳定性方面，系统对数据库持久化和 VLM 处理均设置了异常捕获。数据库异常不会直接阻断实时监控，VLM 分析异常会记录日志并释放待处理状态。停止监控时，系统会统计当前座位数、警告数、提示数和事件数，并更新会话结束信息。最终提交论文前，建议从日志中统计检测耗时、VLM 延迟、事件生成数量和接口响应情况，形成更完整的性能分析表。

## 5.7 存在问题与优化方向

系统当前仍存在一些不足。首先，异常识别准确性依赖标注数据规模、标注质量、检测模型和测试视频质量。若课堂摄像头角度不佳、光照不足、遮挡严重或学生目标过小，检测结果可能不稳定。其次，系统当前使用规则阈值进行告警判断，规则具有可解释性，但对不同班级、不同课程和不同课堂活动的适应性有限。第三，VLM 复核依赖外部 API，受网络、费用、调用限制和响应延迟影响。第四，系统目前主要验证单路课堂视频，尚未实现多教室并发任务调度。第五，隐私保护还可以进一步加强，例如对截图访问进行更严格鉴权，对学生面部进行模糊处理，对访问日志进行脱敏。

后续优化方向包括：第一，继续扩大课堂行为标注数据集，补充不同机位、不同课程和不同光照条件下的样本，并定期重新训练模型。第二，引入姿态估计或时序动作识别方法，使系统不仅依赖检测框类别，还能利用关键点和动作变化。第三，优化 SAHI 切片策略和模型推理方式，提高实时性。第四，将 VLM 复核改为可配置模块，根据场景选择本地模型或云端模型。第五，完善教师复盘统计，例如按课堂时间段统计异常分布，按座位统计事件频次，生成课后报告。第六，加强隐私合规设计，明确数据保存周期、访问权限、脱敏策略和删除机制。

## 5.8 本章小结

本章从测试环境、功能测试、接口权限测试、模型训练评估方案、异常识别案例、实时性与稳定性以及存在问题等方面对系统进行了分析。系统已经具备登录鉴权、实时监控、异常检测、事件持久化、VLM 复核、历史查询和教学复盘等主要功能，能够支撑毕业设计的系统实现要求。模型评估部分进一步明确了 Precision、Recall、mAP、混淆矩阵和推理耗时等计算机视觉指标，使论文能够体现数据集整理、模型训练和系统落地之间的关系。但系统仍需在更大规模真实测试数据、长期运行统计和隐私保护方面进一步完善。

## 结论

本文围绕课堂教学管理中异常行为发现不及时、事件记录不完整、课后复盘缺少客观依据等问题，设计并实现了一套课堂异常行为智能检测系统。系统采用前后端分离架构，后端基于 FastAPI 提供认证、监控控制、视频流、WebSocket、历史记录和复盘接口，前端基于 Vue 3 和 Ant Design Vue 实现实时监控、异常通知、历史查询和课堂复盘页面。系统从课堂视频样本整理、行为类别标注、YOLO 模型训练与部署出发，综合使用 OpenCV 视频读取、YOLO/SAHI 检测、匈牙利座位匹配、滑动窗口告警规则、多模态视觉模型复核和 MySQL 数据持久化，形成了从数据准备到模型检测、从异常事件展示到课后复盘的完整业务闭环。

从设计结果看，系统具有以下特点。第一，系统结构完整，覆盖用户登录、班级权限、实时监控、异常识别、事件保存、历史查询和复盘管理。第二，人工智能应用链路较完整，包含数据集整理、类别标注、YOLO 训练、分片推理、规则判定和 VLM 复核。第三，数据库模型能够保存监控会话、座位、事件、截图、模型复核和教学复盘等关键数据，满足后续查询与统计需求。第四，前端页面能够将视频画面、检测框、统计卡片和事件通知整合展示，方便教师理解系统输出。

本文的主要创新点可以概括为五个方面：一是面向课堂异常行为场景，设计了包含正常、低头、趴桌、转头和吃东西的行为标注体系，并将其与 YOLO 模型训练和后端状态映射打通；二是面向课堂大画面的小目标问题，将 SAHI 分片检测引入课堂行为检测流程；三是面向座位管理需求，通过匈牙利匹配保持学生座位编号的连续性；四是面向误报控制问题，使用滑动窗口规则将短时检测结果转化为持续性告警；五是面向教学复盘需求，将 VLM 语义复核、事件截图、历史会话和教师复盘表单整合为闭环。上述创新属于人工智能应用层面的组合创新，能够较好体现计算机视觉技术在教学管理场景中的实践价值。

本文系统也存在不足。系统当前主要基于测试视频进行验证，尚未在真实课堂环境中进行长期运行测试；标注数据规模和类别覆盖仍有扩展空间，模型量化评估还需要结合真实训练日志持续补充；VLM 复核依赖外部接口，存在网络和费用方面的限制；隐私保护机制仍需进一步加强。后续研究可从数据集扩充、模型训练优化、姿态估计、多路视频并发、复盘报告生成和数据安全合规等方面继续改进。

总体而言，本文完成的课堂异常行为智能检测系统达到了毕业设计的基本目标。系统能够围绕课堂异常行为辅助识别这一具体应用场景，完成需求分析、数据准备、模型构建、系统设计、模块实现和测试分析，具有一定人工智能应用价值、工程实践价值和继续完善空间。
