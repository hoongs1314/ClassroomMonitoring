## 摘要

针对课堂教学中学生状态观察、异常行为记录和课后复盘需求，本文设计并实现了一套基于 YOLO 与视觉语言模型的课堂异常行为检测与分析系统。系统以课堂视频为输入，结合目标检测、SAHI 分片推理、座位关联和滑动窗口判定，对学生课堂行为进行周期性分析与事件记录；通过多模态视觉模型对异常截图进行语义复核，为教师提供更具可读性的辅助说明。系统采用前后端分离架构，完成用户登录、班级管理、课堂监控、异常告警、历史记录和教学复盘等功能设计与实现。教师可在课堂教学期间查看分析过程和阶段性事件，也可在课后查看完整的监控记录与复盘内容。论文围绕相关技术、需求分析、系统总体设计、关键模块实现和测试方案展开论述，形成从课堂视频处理、行为识别到教学复盘的完整业务流程，为计算机视觉技术在智慧课堂管理中的应用提供实践参考。

关键词：课堂异常行为；SAHI 分片检测；座位关联；视觉语言模型；教学复盘

## 前言

近年来，教育数字化与人工智能技术持续发展，智能技术逐步进入教学、学校管理和教育治理等应用环节。2025 年发布的《中国智慧教育白皮书》与国家教育数字化战略行动 2.0，为智能技术服务教育教学与教育治理提供了发展方向[16]。2026 年，教育部等五部门印发《“人工智能+教育”行动计划》，提出以应用为导向，推动人工智能融入教育全要素、全过程和全场景[17]。上述政策部署为课堂视频分析、教学过程记录和课后复盘提供了明确的应用方向与技术条件。

在这一应用导向下，课堂作为学校教学活动的基本场所，既是知识讲授和师生互动发生的主要空间，也是教学过程分析的重要场景。教师在课堂中承担学生状态关注、课堂互动组织和秩序维护等工作；对于人数较多的班级，教师需要在授课过程中及时掌握学生的姿态变化和课堂行为。课堂异常行为智能检测系统以课堂视频为输入，形成异常事件记录与复盘材料，为教学反馈、课堂秩序维护和学生学习状态改善提供辅助依据，具有明确的研究与应用价值。

近年来，深度学习在目标检测、姿态估计和图像理解等方向取得了较快发展。课堂状态识别与课堂行为检测研究已将目标检测、特征融合和系统应用结合起来，用于处理学生行为类别识别、远景小目标和复杂遮挡等问题[1-4]。但是，课堂场景具有目标密集、遮挡较多、学生距离镜头较远、画面分辨率较高、异常行为边界不清晰等特点。单纯依靠检测模型输出类别，容易将正常写字、看书、低头阅读等行为误判为异常。为降低此类误判，系统需要结合时序规则、局部截图复核和人工复盘机制，形成稳妥的工程方案。

本文设计的课堂异常行为智能检测系统围绕“课堂期间分析、证据保存、课后复盘”的教学管理需求组织软件功能。检测结果经座位关联和连续状态判定后形成事件记录，再由局部截图复核补充原因说明。教师可以在课堂监控、历史记录和复盘页面中查看相应信息，使模型输出进入可追踪的业务流程。

本文系统将人工智能识别结果嵌入完整教学业务链路：通过分片检测和座位匹配提高课堂大画面中学生目标的可用性；通过滑动窗口规则将单帧结果转化为持续性告警事件；通过多模态视觉模型对异常截图进行语义复核，使事件具备可读原因；通过历史记录和教学复盘形成课后分析材料。这些设计体现了面向真实课堂场景的工程应用价值。

本文的主要工作包括：分析课堂监控的角色权限与业务需求；设计从数据整理到模型部署的实现流程；构建前后端分离架构与数据存储结构；实现视频处理、事件生成、状态推送和复盘管理模块；建立功能测试与模型评估的填写框架。全文按“研究基础、需求分析、总体设计、关键实现、测试方案”的顺序展开。

本文结构安排如下：第一章介绍课堂异常行为检测涉及的相关技术和理论基础；第二章从应用场景、用户角色、功能需求和非功能需求等方面进行系统需求分析；第三章给出系统总体架构、业务流程、数据库结构、接口通信和部署设计；第四章详细说明数据集整理、模型训练和系统关键模块的设计与实现；第五章从功能测试、接口测试、模型评估方案、异常识别案例和系统稳定性等方面进行测试与分析；最后给出结论、总结与体会、谢辞、参考文献和附录。

# 第一章 研究基础与相关工作

## 1.1 课堂异常行为智能检测研究背景

课堂行为识别是教育信息化和计算机视觉交叉应用中的一个具体方向。传统课堂观察通常依赖教师经验或人工听课记录，这种方式能够体现教育判断，但难以形成持续、细粒度和可追溯的数据记录。随着摄像设备、边缘计算、深度学习模型和 Web 应用技术的发展，课堂视频可以成为教学过程分析的重要数据来源。相关研究表明，基于视觉线索的课堂行为计算可以捕捉教师和学生的课堂状态，为教学互动分析和学习状态反馈提供支持[1,6]。这说明课堂行为识别具有明确应用价值，但同时也要求系统设计者谨慎处理行为定义、误判风险和隐私保护问题。

课堂异常行为识别需要识别学生目标，并结合学生姿态、课堂语境、持续时间、发生频率、检测置信度、截图可见区域和教师复盘结果进行综合判断。低头、身体前倾和转头等状态需要通过头肩姿态、桌面关系、持续动作和课堂活动内容进行区分。

从工程实践角度看，课堂异常行为智能检测系统定位为教师教学管理的辅助工具。系统输出采用“疑似”表述，多模态视觉模型提示词围绕可见学生姿态生成说明，并以“疑似”语气呈现异常结论。这种设计体现了教育场景中技术使用的边界意识。

## 1.2 相关研究进展与问题分析

课堂行为研究通常遵循“场景难点界定、针对性方法设计、实验验证、系统应用”的叙述逻辑。张冬环[1]将课堂表情识别与行为识别结合，并实现课堂状态分析系统，说明课堂分析可以由单一识别任务延伸至教师反馈环节。曹倩等[2]从特征融合、检测头、主干模块和回归损失等方面改进课堂行为检测。黄日顺和陈世国[3]针对目标密集、遮挡和尺度差异调整检测结构。傅圣深等[4]则从细粒度特征、多尺度融合和小目标检测层提升远景课堂行为识别能力。上述研究为课堂小目标、遮挡和尺度变化问题提供了有针对性的思路。

曾钰琦等[15]面向智慧教育场景，围绕学生课堂行为检测中的目标密集、遮挡、尺度变化和样本不均衡问题改进 YOLOv8 模型。该研究表明，模型结构设计和数据分布都会影响课堂行为检测效果，可为本项目后续开展模型训练与离线评估提供参考。

除了模型结构外，课堂场景还需要处理标注成本、类别分布和伪标签噪声等问题。张睿等[5]针对密集课堂提出类内感知半监督策略，说明数据利用效率会影响系统可用性。课堂行为智能识别通过连续状态判断、证据解释和数据治理记录发生时段、持续时间和复盘依据。

刘清堂等[6]从数据采集与存储、行为建模与计算、智能服务三个模块开展课堂教学行为分析。董琪琪等[7]采用改进 SSD 方法识别学生课堂行为状态，谭暑秋等[8]面向教室监控场景开展学生异常行为检测。崔家郡等[9]进一步梳理了课堂师生交互的图像、语音、文本与多模态智能分析技术。上述研究说明，课堂行为分析需要同时考虑视觉识别结果、行为上下文和教学应用环节。

针对细粒度行为线索，李佳楠等[10]利用多尺度特征图卷积网络开展教学行为识别与分析；周宇航等[11]将 AlphaPose 用于课堂行为识别。相关工作为结合姿态线索和多尺度特征细化行为判断提供了参考。本项目采用“检测、规则、复核”的实现方式，围绕低头书写、伏案休息和侧身交流等相近状态保留人工复盘依据。

因此，本文将研究问题界定为：在既有行为检测模型基础上，构建稳定关联座位、抑制短时误报、提供语义解释并保存复盘证据的课堂异常行为辅助识别系统。评价重点包括离线检测指标、事件规则可解释性、系统功能完整性、权限边界和实验可复现性。

## 1.3 目标检测技术概述

目标检测是计算机视觉中的基础任务，目标是在图像中定位特定类别对象并输出边界框和类别信息。随着深度学习的发展，基于卷积神经网络的检测方法已广泛用于视频分析。YOLO 系列模型将目标定位和类别判断整合在同一推理流程中，适合本项目的课堂视频处理需求[12]。

在课堂场景中，学生目标分布密集，检测框之间距离较近，后排学生的姿态细节受缩放比例影响，不同教室、班级和视频源的光照、角度与分辨率也存在差异。异常行为类别由桌面可见性、上半身姿态和画面裁剪范围等因素共同决定，例如“低头”和“趴桌”需要结合多个视觉线索进行区分。

本系统以目标检测作为第一阶段识别手段，将检测模型输出映射为 NORMAL、HEAD_DOWN、DESK_LYING、TURNING_HEAD 和 EATING 等状态码，再由滑动窗口规则生成“提示”或“警告”级别事件。连续窗口结合遮挡、模糊和姿态变化信息过滤短时波动，形成稳定的告警记录。

课堂行为数据集覆盖不同座位区域、光照条件、学生姿态和画面清晰度，并对类别边界作出统一规定。正常写字与疑似低头的标注结合头部朝向、上半身姿态、持续动作和桌面关系进行判断；趴桌与低头通过头肩位置、身体倾斜程度和桌面接触情况进行区分。数据标注将课堂管理问题转化为可训练视觉类别，是模型训练的关键环节。

YOLO 模型训练包括数据划分、标注格式转换、预训练权重加载、数据增强、训练迭代、验证集评估和模型导出等步骤。本文围绕课堂异常行为核心类别完成模型训练，并以 `.pt` 权重文件形式嵌入后端推理流程。模型评估重点关注 Precision、Recall、mAP、混淆矩阵和典型误检样例，用于分析低头、趴桌、转头和吃东西等类别的识别效果。

## 1.4 分片检测技术

本项目采用的分片推理方法将原始课堂画面切分为若干重叠区域，分别完成目标检测后再映射回原图并合并结果。对于后排学生较小、整图缩放后细节不足的课堂画面，该方法可为检测模型提供更细的局部输入。SAHI 方法为切片推理与结果合并提供了通用实现思路[13]。分片数量、重叠比例和结果合并阈值需结合真实测试记录确定。

课堂监控画面通常是固定机位拍摄的宽幅视频，前排学生目标较大，后排学生目标较小。如果直接对整帧图像缩放到固定输入尺寸，后排学生的头肩和上半身细节可能不足，导致检测结果不稳定。采用 SAHI 分片推理后，局部画面在推理前能保留更多像素细节，有利于提高小目标可见性。本文系统在后端检测循环中通过 `get_sliced_prediction` 对当前视频帧进行切片检测，切片高度和宽度均设置为 640，并在后处理中合并检测结果。这一设计与课堂画面中目标密集、大小差异明显的特点相匹配。

SAHI 通过多子图推理提升局部目标可见性，系统据此配置周期性检测流程。本文系统将检测循环设置为周期性执行，每轮检测后间隔约 2 秒，并为达到告警条件的座位执行 VLM 复核，以形成课堂事件记录和稳定的计算流程。

## 1.5 多模态视觉模型复核技术

多模态视觉模型能够依据图像和文字约束生成描述或判断。在课堂异常行为识别场景中，检测模型输出类别和边界框，多模态视觉模型为触发事件的局部截图补充语义说明，并使用“疑似”语气呈现结果。

本系统将 VLM 复核设置为第二阶段。检测层通过 YOLO/SAHI 输出初步类别，滑动窗口规则筛选达到告警条件的座位并加入 VLM 队列。VLM 接收目标学生裁剪图，并按照系统提示词输出 JSON 对象，字段包括 `status`、`label`、`confidence` 和 `reason`。`status` 使用 NORMAL、HEAD_DOWN、DESK_LYING、TURNING_HEAD、EATING、UNCERTAIN 和 EMPTY 等状态值；其中，异常结果用于补充事件说明并保存复核记录。

在教育场景中，VLM 提示词围绕可见学生姿态和课堂行为生成说明。截图模糊、目标过小或遮挡严重时，模型返回 UNCERTAIN 和“无法确定”；截图中没有可分析学生时，模型返回 EMPTY 和“未看到可分析学生”，使输出符合教学辅助场景的使用要求。

## 1.6 系统开发技术基础

本系统使用后端服务框架提供登录鉴权、监控控制、视频流、状态推送、历史会话和教学复盘接口；前端通过组件化页面展示视频画面、座位状态、异常事件和复盘信息；关系型数据库保存用户、班级、监控会话、异常事件和复盘记录等结构化数据。服务端周期性推送状态，视频画面与事件数据独立传输，支持课堂期间查看与课后完整分析。上述技术选型支撑项目实现。

## 1.7 本项目研究定位与技术路线

本文采用“快速检测、连续判定、语义复核、业务留痕”的分层技术路线。检测层输出候选行为和边界框；关联层维持座位编号；规则层根据连续状态生成提示或警告；复核层为已触发事件补充可见依据；业务层保存事件并供教师复盘。模型参数、规则阈值和运行效果均以实际实验记录为准。

本文遵循“问题界定、模块设计、实现说明、实验验证”的叙述顺序，重点说明系统如何将识别结果转化为可审查的课堂事件。模型对比、耗时统计和使用反馈以实际实验记录进行分析。

# 第二章 系统需求分析

## 2.1 系统应用场景分析

本文系统面向普通课堂教学场景，主要服务对象是需要进行课堂状态观察、异常事件记录和课后教学复盘的教师或管理员。系统的基本使用流程为：用户登录系统后选择有权限查看或启动监控的班级；教师进入课堂监控页面，启动视频分析；系统读取对应班级的视频源，按周期执行检测分析并记录阶段性事件；课堂教学期间，教师可查看视频画面、学生人数、警告数、提示数和异常事件列表；课堂结束后，教师可进入历史监控页面查看完整会话记录，并在复盘页面填写课堂专注情况、主要问题和改进计划。

该应用场景具有三个特点。第一，系统支持课堂期间按需查看，教师能够结合教学过程查看阶段性分析结果。第二，系统保存异常截图、事件时间、座位编号、检测类别和模型说明，为课后完整复盘提供事件证据。第三，系统按照班级授权范围提供监控记录查看和复盘功能，管理员负责系统管理。系统形成从用户登录、课堂分析到课后复盘的闭环业务流程。

课堂异常行为检测系统围绕“少误报、能解释、可追踪、能复盘”组织功能。本文系统将课堂异常行为识别划分为检测、规则、复核、留痕和复盘五个环节，结合单帧检测类别、事件截图、权限控制和复盘入口，为教师提供完整的教学管理支持。

## 2.2 用户角色与权限需求分析

系统主要包括管理员和教师两类用户。管理员负责系统初始化、账号维护、班级与测试视频配置、教师班级授权和整体监控记录查看；教师负责查看自己有权限的班级、启动课堂视频分析、查看阶段性异常事件和填写教学复盘。系统数据库中通过 `sys_user`、`sys_role` 和 `sys_user_role` 保存系统账号与角色关系，通过 `edu_teacher` 保存教师档案，通过 `edu_teacher_class` 保存教师与班级的授权关系。

权限需求主要包括以下内容。首先，用户登录后可访问课堂监控、视频流、WebSocket、班级列表和历史记录等接口。其次，教师按照班级授权范围查看监控、启动视频分析和进行复盘。再次，管理员提交复盘时可指定教师 ID，使复盘记录关联到具体教师。最后，系统记录登录情况和认证令牌，便于追踪用户会话和处理登出、刷新令牌等操作。

从项目实现看，后端依赖模块负责解析 Bearer token 并加载当前用户上下文，教师业务路由通过 `_allowed_class_ids` 和 `_ensure_session_access` 等函数校验班级访问范围，课堂监控接口根据班级查看或启动权限提供服务。这些设计使系统满足毕业设计中对用户管理和权限控制的基本要求。

## 2.3 课堂视频分析与监控功能需求

课堂视频分析与监控是系统的核心功能。系统支持教师选择班级并启动视频分析，后端根据班级名称或班级编码切换对应视频源，读取视频帧并按周期执行检测分析。前端显示当前班级、连接状态、监控阶段、课堂视频画面、座位检测框、学生人数、警告数量、提示数量和异常行为通知。教师可以在课堂教学期间按需查看分析结果，也可以在课后通过历史记录和复盘页面查看完整会话信息与事件材料。

具体功能需求包括：第一，系统应支持多个班级视频源配置，例如 1 班、2 班、3 班和 4 班分别对应不同测试视频，管理员可维护班级信息和视频源配置。第二，系统应在启动监控时创建监控会话，记录班级、教师、操作人、视频路径、画面宽高和开始时间。第三，系统应持续读取视频帧并更新前端画面。第四，系统应对每轮检测结果维护座位状态，并在前端叠加显示。第五，系统应定时向 WebSocket 客户端推送结构化状态，使前端无需频繁轮询即可获取最新数据。第六，系统停止监控时应保存结束时间、学生总数、警告数、提示数和事件总数。

## 2.4 异常行为识别与告警需求

系统识别正常、疑似低头、疑似睡觉、疑似转头和疑似吃东西五类课堂状态，并采用“疑似”语气呈现辅助判断结果。后端将检测类别映射为状态码，其中 0 对应 NORMAL，1 对应 HEAD_DOWN，2 对应 DESK_LYING，3 对应 TURNING_HEAD，4 对应 EATING。系统根据滑动窗口统计最近几次检测状态，当疑似睡觉达到阈值时生成“警告”，当低头、转头和吃东西等低级异常合计达到阈值时生成“提示”。

告警需求包括检测规则层和视觉模型复核层。检测规则层将连续检测结果转化为业务事件：连续多次出现低头、转头或吃东西状态时生成提示，疑似睡觉达到相应阈值时标记为警告。视觉模型复核层为已触发告警的局部截图补充中文标签和判断原因，使教师能够理解系统判断依据。

## 2.5 历史记录与教学复盘需求

课堂监控系统提供课堂期间分析和课后复盘功能。系统保存每次监控会话及其异常事件，使教师能够回顾某次监控过程的整体情况。历史记录页面按班级筛选监控会话，展示班级、教师、状态、开始时间、警告数、提示数和操作入口。复盘页面展示会话概要、异常事件截图、事件标签和模型原因，并提供教学效果评分、课堂专注情况、主要问题和改进计划等填写项。

教学复盘需求体现了系统从“检测工具”到“教学管理工具”的转变。异常事件本身只是客观记录，教师需要结合课堂活动和学生实际情况进行解释。例如，某段时间学生普遍低头可能是正在做题或阅读资料，也可能是课堂参与度不足。系统通过保存事件截图和时间点，为教师提供复盘依据，但最终教学判断仍应由教师完成。

## 2.6 系统非功能需求

系统非功能需求主要包括分析时效性、稳定性、可维护性、安全性和可部署性。项目通过后台线程分别处理视频帧读取、检测分析和 VLM 队列任务，按周期更新课堂视频和状态。`_safe_persist` 对持久化操作进行异常捕获，VLM worker 对分析过程进行日志记录，保障课堂视频分析与事件记录的连续运行。

可维护性要求系统代码按职责分层。项目将后端入口、配置、数据库、鉴权依赖、领域模型、业务路由、监控服务和视频工具分别放在不同目录，前端也按视图、组件、布局、组合式函数和样式文件组织。安全性通过登录鉴权、班级授权范围和接口校验保护课堂画面与监控数据。可部署性支持本地和 Docker 环境运行，项目提供 `docker-compose.yml`，将 MySQL、后端和前端容器组合部署。

## 2.7 本章小结

本章从应用场景、用户角色、课堂视频分析、异常识别、历史复盘和非功能需求等方面分析了系统需求。课堂异常行为智能检测系统需要完成从视频输入到异常事件输出、从课堂期间查看到历史复盘、从检测模型到教师决策支持的完整流程。需求分析表明，系统具备计算机视觉处理能力、业务权限管理、数据存储和交互展示能力。

# 第三章 系统总体设计

## 3.1 系统总体架构设计

系统采用前后端分离架构，整体可划分为用户访问层、部署与代理层、后端服务层、智能分析层、数据准备与文件层。用户访问层由教师或管理员浏览器和 Vue 前端组成，负责登录、账号与班级管理、监控展示、历史记录和教学复盘。部署与代理层由 Nginx 前端容器和 Docker Compose 组成，负责静态资源服务、反向代理和多容器编排。后端服务层由 FastAPI 应用、认证路由、管理员路由、教师业务路由、配置与数据库模块、鉴权依赖、监控服务和视频读取工具组成。智能分析层由 YOLO 模型训练与部署、SAHI 分片检测、滑动窗口规则、多模态视觉模型和 VLM 提示词组成。数据准备与文件层由课堂视频样本、标注数据、模型文件、异常截图输出目录、MySQL 数据库和初始化 SQL 组成。

系统总体数据流如下：在模型构建阶段，先从课堂视频中抽取样本帧，完成学生行为框选、类别标注、数据划分和 YOLO 训练，导出可部署的检测权重；在系统运行阶段，教师登录系统后选择班级并启动监控，前端发送启动请求到后端，后端校验 token 和班级权限后创建监控会话，视频读取线程持续获取当前帧，检测线程定期对当前帧进行 SAHI 分片检测，检测结果进入座位匹配和滑动窗口规则，达到告警条件时保存异常截图和事件记录，VLM worker 对异常截图进行复核并更新事件说明，后端通过 WebSocket 周期性推送状态给前端。教师可在课堂期间查看视频画面和阶段性事件，也可在课后进入历史页面和复盘页面查看完整会话并填写复盘内容。

## 3.2 课堂视频分析业务流程设计

课堂视频分析流程是系统的核心业务流程。流程开始于教师点击“启动监控”。前端携带 access token、班级编码、教师 ID 和操作人信息请求后端启动接口。后端校验用户身份和班级启动权限，根据班级编码解析运行时班级名称，并切换视频源。系统创建监控会话后，将 `state["is_running"]` 设置为 True，重置检测状态、VLM 队列和告警映射。

后台帧读取线程持续从当前视频源读取最新帧，检测线程在监控运行时获取当前帧并调用 SAHI 检测。检测结果包含边界框和类别 ID。由于同一学生在连续帧中的检测框位置可能发生变化，系统通过匈牙利算法将新检测框与已有座位进行匹配，尽量保持座位编号稳定。匹配完成后，系统根据检测类别更新每个座位的滑动窗口。若连续 NORMAL 达到恢复阈值，则清除该座位告警状态；若疑似睡觉次数或其他异常次数达到阈值，则生成异常事件。

事件生成后，系统裁剪目标座位区域并保存到 `outputs/event_crops`，同时在数据库中写入 `monitor_behavior_event` 和 `monitor_event_frame`。达到告警条件的座位按照送检间隔和待处理集合进入 VLM 队列。VLM 返回异常结果后，后端更新事件标签、原因和复核记录。前端通过 WebSocket 接收状态数据，周期性更新统计卡片、检测框和事件列表。

## 3.3 数据库结构设计

系统数据库可分为三组：系统权限表、教学基础数据表和监控业务表。系统权限表包括 `sys_user`、`sys_role`、`sys_user_role`、`sys_auth_token` 和 `sys_login_log`。这些表用于保存用户账号、角色、用户角色关系、认证令牌和登录日志。教学基础数据表包括 `edu_teacher`、`edu_class` 和 `edu_teacher_class`。这些表用于保存教师档案、班级与教师班级授权关系。监控业务表包括 `monitor_session`、`monitor_session_seat`、`monitor_behavior_event`、`monitor_event_frame`、`monitor_vlm_review` 和 `monitor_teaching_review`。

`monitor_session` 是监控会话主表，用于记录一次课堂监控的开始、结束和统计信息。其字段包括会话编号、班级 ID、班级名称、教师 ID、操作人、视频路径、图像宽高、状态、开始时间、结束时间、学生总数、警告数、提示数、事件数以及检测、VLM 和规则配置。`monitor_session_seat` 保存一次会话中识别到的座位信息，包括运行时座位 ID、座位编号、检测框坐标、状态、检测类别、分析来源和锁定状态。`monitor_behavior_event` 保存异常事件，包括事件 UID、会话 ID、班级 ID、座位 ID、座位编号、告警等级、状态码、中文标签、原因、来源、图片地址、边界框和事件时间。

`monitor_event_frame` 保存事件截图帧，用于将异常事件与具体截图关联。`monitor_vlm_review` 保存异常 VLM 复核结果，包括模型名称、请求图片、原始响应、解析状态、中文标签、原因、成功标记和延迟。`monitor_teaching_review` 保存教师课后复盘内容，包括教学效果评分、课堂专注情况、主要问题、改进计划和复盘时间。通过这些表，系统能够把课堂视频分析结果转化为可查询、可复盘、可统计的业务数据。

## 3.4 后端接口与 WebSocket 通信设计

后端接口分为认证接口、管理员接口、课堂监控接口和教师业务接口。认证接口用于用户登录、刷新令牌、获取当前用户信息和登出。管理员接口用于维护账号、教师档案、班级、测试视频和教师班级授权。课堂监控接口用于获取班级列表、切换班级、启动监控、停止监控、获取最新帧、访问视频流和建立 WebSocket 连接。教师业务接口用于查询授权班级、历史监控会话、会话详情、会话事件、事件详情以及获取和保存教学复盘。

视频流接口通过查询参数携带 token，后端统一从 Header 或 query 中解析 token。WebSocket 连接通过 query token 或请求头加载用户上下文。连接建立后，后端将客户端加入连接集合并记录可访问的班级范围；广播状态时，系统按授权班级范围筛选状态数据。

WebSocket 推送内容包括运行状态、时间、图像宽高、当前班级、班级列表、座位数组、事件数组和统计数据。前端接收后将其映射为统计卡片、座位框、事件列表和页面状态标签。WebSocket 推送结构化状态，视频画面通过 MJPEG 接口单独获取，使状态数据和图像数据解耦，降低单个通道的处理复杂度。

第三，采用“模型检测 + 规则判定 + VLM 复核”的分层识别策略。检测模型完成目标定位和初步分类，滑动窗口规则结合连续状态生成事件，VLM 复核为局部截图提供自然语言原因说明。三层结合后，系统具备分析时效性、可解释性和可调整性。

第四，面向课堂座位场景设计了稳定的座位关联机制。课堂管理记录“哪个座位在什么时间出现什么状态”。系统通过匈牙利算法维护连续帧中的座位编号，使异常事件关联到稳定座位编号，便于前端展示、数据库记录和课后复盘。

第五，系统在教育场景中加入隐私和权限边界。VLM 提示词围绕可见学生姿态生成说明，后端对视频流、WebSocket 和监控接口进行登录鉴权，并根据教师班级权限过滤数据。该设计符合课堂场景对数据安全和谨慎判断的要求。

第六，系统具备较好的工程落地性。项目包含检测逻辑、前端界面、后端接口、数据库模型、权限管理、Docker 部署和文档图表，形成可运行、可演示、可维护的完整毕业设计项目。

# 第四章 系统关键模块设计与实现

## 4.1 视频帧读取与班级视频切换模块

视频帧读取模块负责为检测线程和视频流接口提供当前课堂画面。系统通过 `MockMonitorStream` 封装本地视频源，`CLASS_VIDEOS` 保存班级与视频文件的映射关系。启动监控后，视频读取组件持续更新最新帧及其尺寸信息，供检测和前端展示共用。

班级切换模块用于在不同课堂视频源之间切换。当用户选择新的班级并具备相应权限时，后端调用 `switch_class` 函数切换视频路径，更新当前班级、图像宽高和最新帧，并初始化 VLM 送检时间、待处理座位集合、检测历史窗口、连续正常计数、告警等级映射、座位列表、事件列表和统计数据，为新监控会话建立独立状态。

视频帧读取和班级切换模块通过全局状态提供当前视频帧，前端通过后端视频流接口展示画面。当前实现使用 `inputs` 目录中预先配置的本地测试视频作为班级视频源，管理员在管理页面选择已有测试视频后即可更新班级配置。

## 4.2 数据集整理与行为类别标注

课堂异常行为检测以高质量样本为基础。本文系统以项目测试视频和后续整理的视频片段为主要数据来源，通过 OpenCV 按固定时间间隔抽帧，再对抽取图片进行筛选和标注。样本筛选覆盖遮挡、后排小目标、光照变化、不同班级视角和典型异常姿态，使数据集覆盖课堂画面中的常见变化。

样本筛选主要包括四类处理。第一，筛除严重模糊、黑屏、画面抖动和主体不可见的图片，保证训练样本质量。第二，去除高度重复帧，保持各类姿态样本的合理分布。第三，保留低头写字、看书、趴桌休息、侧身交流等边界样本，增强模型对相近状态的区分能力。第四，对涉及学生面部或个人信息的图片进行使用范围控制，论文展示时进行遮挡或模糊处理。

本文将课堂行为检测类别设计为五类：NORMAL、HEAD_DOWN、DESK_LYING、TURNING_HEAD 和 EATING。NORMAL 表示正常听课、书写、阅读和看黑板等课堂状态；HEAD_DOWN 表示头部明显朝向桌面或视线长时间偏离正常听课方向，上身保持坐姿；DESK_LYING 表示头部或上半身明显接近桌面，具有疑似睡觉或趴桌特征；TURNING_HEAD 表示头部明显转向侧方或后方，偏离主要教学方向；EATING 表示画面中出现手部靠近嘴部、食品包装、进食动作等可见特征。类别定义服务于系统告警和教师复盘，并采用“疑似”语气呈现异常状态。

标注时采用 YOLO 目标检测常用的边界框格式。每个标注框尽量覆盖学生头肩和上半身关键区域，框过小可能丢失姿态信息，框过大则容易引入周围同学和桌椅干扰。标注文件中每一行包含类别编号、归一化中心点坐标、归一化宽度和高度，即 `class x_center y_center width height`。本文系统中的类别编号与业务状态一一对应：0 对应 NORMAL，1 对应 HEAD_DOWN，2 对应 DESK_LYING，3 对应 TURNING_HEAD，4 对应 EATING。通过这种设计，训练数据、检测模型和后端业务状态可以保持一致，降低模型部署时的映射成本。

数据集划分时应将样本分为训练集、验证集和测试集。需要注意的是，同一视频片段中相邻帧高度相似，如果随机混合划分，可能造成训练集和测试集内容过于接近，导致评估结果偏高。更稳妥的方式是按视频片段、班级或时间段进行分组划分，使测试集尽量包含模型训练阶段未见过的场景。标注完成后，还应进行二次复核，重点检查类别边界、框选范围、漏标、多标和类别不平衡问题。对于样本较少的类别，例如 EATING，可通过补充视频片段或有控制地增加数据增强来缓解类别不均衡。

## 4.3 YOLO 模型训练与检测模型构建

YOLO 模型训练的目标是识别课堂画面中的学生行为状态，并输出后端可直接使用的类别和边界框。本文系统采用迁移学习思路，在通用预训练权重基础上进行课堂行为数据微调，利用通用视觉特征和课堂行为标注数据学习具体姿态类别。

训练配置主要包括输入尺寸、批量大小、训练轮次、学习率、数据增强和早停策略。考虑到系统运行时 SAHI 切片尺寸为 640，训练输入尺寸也可设置为 640，以减少训练和部署之间的尺度差异。数据增强可以使用缩放、平移、亮度变化、轻微裁剪等方式提高模型对不同画面条件的适应能力；水平翻转应结合课堂方向谨慎使用，因为翻转后可能改变学生面向讲台的空间关系。训练过程中需要观察训练损失、验证损失、Precision、Recall、mAP50 和 mAP50-95 等指标，判断模型是否出现欠拟合或过拟合。

模型评估结合总体 mAP 与课堂业务需求分析各类别表现。评估结果通过混淆矩阵和典型预测样例展示 NORMAL、DESK_LYING、HEAD_DOWN、TURNING_HEAD 和 EATING 等类别的识别情况，并对低头写字、看书、趴桌和侧身交流等边界样本进行单独观察，为系统规则阈值调整提供依据。

训练完成后，模型以 `.pt` 权重文件形式保存，并在系统运行时由后端检测模块加载。项目中检测模型路径为 `models/gmn26n-behavior.pt`，后端通过 Ultralytics 模型封装完成推理，再结合 SAHI 分片检测适配高分辨率课堂画面。本文围绕数据集构建、模型训练、分片推理、规则告警和业务复盘组织人工智能应用开发过程。

## 4.4 基于 YOLO 与 SAHI 的课堂行为检测模块

检测模块位于 `backend/services/monitor_service.py`。系统在检测分析循环中加载基于 Ultralytics 的检测模型，模型路径为 `models/gmn26n-behavior.pt`，置信度阈值设置为 0.25，输入尺寸设置为 640。每轮检测时，系统调用 SAHI 的 `get_sliced_prediction` 对当前帧进行分片预测，切片高度和宽度均为 640，并设置后处理匹配阈值。检测结果以对象预测列表形式返回，其中包含边界框坐标和类别 ID。

检测类别通过 `CATEGORY_TO_STATUS` 映射为业务状态。类别 0 表示 NORMAL，类别 1 表示 HEAD_DOWN，类别 2 表示 DESK_LYING，类别 3 表示 TURNING_HEAD，类别 4 表示 EATING。系统基于这些状态执行滑动窗口规则，在连续状态达到阈值后生成事件记录。

检测模块输出用于事件生成和前端座位框显示。每个检测框会被格式化为 `[x1, y1, x2, y2]` 坐标，并与座位编号绑定。前端视频组件根据后端返回的座位数组，在视频画面上绘制对应检测框和状态信息，使教师能够直观看到系统识别位置。课堂行为检测模型结合 SAHI 分片推理，为大画面、多学生、小目标场景提供初步视觉结果。

## 4.5 基于匈牙利算法的座位匹配模块

在连续视频帧中，同一学生的检测框位置会随姿态、遮挡和检测误差产生变化。如果每次检测都重新生成座位编号，前端显示和事件记录会变得混乱。因此系统需要在新检测框与已有座位之间建立匹配关系。本文系统采用匈牙利算法解决匹配问题，该算法面向分配问题寻找整体代价较小的匹配方案[14]。

系统首先计算每个检测框的中心点和宽高，并以检测框最长边的平方作为最大匹配距离阈值。随后构建代价矩阵，矩阵行表示当前检测框，列表示已有座位和虚拟新座位列。系统将阈值内的中心点距离作为匹配成本，将超出阈值的候选项保留为极大值；虚拟列使用固定成本，为新检测框分配新的座位编号。最后由最优匹配求解器完成座位关联。

匹配完成后，如果检测框匹配到已有座位，系统更新该座位的检测框和检测类别；如果匹配到虚拟列，则创建新的座位编号。座位编号格式为 `S01`、`S02` 等，前端和数据库都使用该编号展示或记录座位。该模块使同一座位在连续检测中保持相对稳定，有利于滑动窗口统计和异常事件归因。

## 4.6 基于滑动窗口的异常告警判定模块

滑动窗口告警模块用于把连续检测状态转化为业务事件。系统为每个座位维护一个长度为 5 的检测历史队列。每轮检测后，系统将该座位当前状态追加到队列中，并更新连续 NORMAL 计数。连续 NORMAL 次数达到 2 时，系统将座位状态恢复为正常，清除告警等级并清空检测历史。

异常告警分为“警告”和“提示”两个等级。疑似睡觉被视为较高风险异常，当滑动窗口中 DESK_LYING 出现次数达到 2 时，系统生成“警告”。疑似低头、疑似转头和疑似吃东西被归为低级异常，当三类状态合计次数达到 3 时，系统生成“提示”。告警等级变化或首次达到阈值时，系统调用 `append_event` 生成异常事件；等级保持一致时更新座位状态。

该规则设计具有工程上的可解释性。教师可以理解系统为什么触发事件，即某个座位在最近几次检测中多次出现某类疑似异常。相比直接使用单帧检测结果，滑动窗口能减少偶然误检。相比完全依赖深度模型，规则层也便于根据学校管理要求调整阈值。例如，如果学校更关注疑似睡觉，可以降低 DESK_LYING 阈值；如果更希望减少误报，可以提高低级异常触发次数。

## 4.7 基于多模态视觉模型的异常复核模块

VLM 复核模块由任务入队、模型调用、结果解析和事件更新四部分组成。系统首先筛选当前处于“警告”或“提示”的座位，再判断该座位是否已经在待处理集合中、是否满足最小送检间隔、检测框宽高比是否适合裁剪。符合条件的座位会与当前帧副本一起进入 VLM 队列。每个 VLM worker 从队列中取出任务，裁剪目标座位局部图像，将图像编码为 base64，并通过 LangChain OpenAI 兼容接口调用 `qwen-vl-max` 模型。

模型系统提示词对输出格式和判断边界进行了严格约束。VLM 必须只输出 JSON 对象，且包含 `status`、`label`、`confidence` 和 `reason` 四个字段。系统提示词还规定，如果截图中没有可分析学生，应输出 EMPTY；如果画面模糊、遮挡严重或判断依据不足，应输出 UNCERTAIN；不要把低头写字、看书、看试卷直接判定为异常；所有异常结论必须使用“疑似”语气。这样的提示词设计降低了模型随意输出的风险，使后端能够稳定解析结果。

VLM 返回结果后，系统通过 `parse_model_json` 解析 JSON，并调用 `apply_vlm_result` 更新事件。VLM 返回异常状态时，复核结果补充事件的 label 和 reason，告警等级由检测规则层生成，事件说明由复核层完善；同一异常结果同步写入 `monitor_vlm_review`。该表保存模型名称、请求截图、原始响应、解析结果、成功状态和延迟，为后续排查和优化提供依据。

## 4.8 监控事件持久化与历史复盘模块

事件持久化模块负责将课堂视频分析结果保存为数据库记录和截图文件。系统生成事件时，会先根据目标座位框裁剪截图并保存到 `outputs/event_crops`，文件名包含事件标识。随后在数据库中创建 `monitor_behavior_event` 记录，字段包括事件 UID、会话 ID、班级 ID、座位 ID、座位编号、告警等级、状态、标签、原因、来源、图片 URL、图片路径、边界框坐标和事件时间。同时，系统创建 `monitor_event_frame` 记录，保存截图 URL、截图路径、座位编号、状态文本和原始 payload。

历史复盘模块通过教师业务路由提供接口。教师可以查询授权范围内的监控会话列表，也可以进入某个会话查看详情和事件列表。事件详情接口会返回事件基本信息和关联截图帧。复盘接口支持获取和保存教学复盘记录，教师可以填写教学效果评分、课堂专注情况、主要问题和改进计划。系统通过 `monitor_teaching_review` 表保存教师与会话对应的复盘记录。

持久化与复盘模块使系统结果具有可追溯性。系统保存事件截图、结构化记录和模型说明，教师可据此开展课后复盘。该模块形成智能识别、事件留痕和教学复盘的完整业务闭环。

## 4.9 教师端课堂监控前端实现

课堂监控前端页面位于 `web/src/views/MonitorView.vue`。页面通过 `useWebSocket` 获取后端推送状态，通过 `useApi` 发送启动和停止监控请求。页面顶部显示系统名称、WebSocket 连接状态、监控阶段标签和启动/停止按钮。主区域左侧为视频面板，使用 `VideoPlayer` 组件加载 MJPEG 视频流，并根据后端返回的座位数组绘制疑似低头、疑似睡觉、疑似转头和疑似吃东西四类异常检测框及状态标签。右侧为统计与事件区域，使用 `StatsCard` 显示学生人数、警告数和提示数，使用 `EventList` 展示异常事件通知。

页面在启动监控时传递班级编码 `X-Class-Code`，并支持传递 URL 编码后的班级名称。用户信息中的教师 ID、操作人 ID 和操作人名称也会随请求头传给后端。系统通过 URL 编码和后端解码传递中文班级名称，视频流 URL 通过 query 参数传入 access token。

课堂监控页面还包含座位图弹窗功能。当教师点击学生人数统计卡片时，可以打开座位图弹窗查看当前座位框分布。异常事件列表中展示的状态标签来自检测或 VLM 复核结果，前端通过 `statusLabel` 将状态码映射为中文说明。整体页面支持教师在课堂教学期间按需查看画面、统计和事件。

## 5.3 接口与权限测试

接口与权限测试的重点是验证系统不会向未授权用户开放课堂视频和监控数据。系统应检查以下情况：未带 token 访问 `/api/classes`、`/api/latest_frame`、`/api/start`、`/api/stop`、`/api/switch_class` 和 `/video_feed` 时，应返回 401；教师访问未授权班级时，应返回 403；教师查看无权访问的历史会话时，应拒绝访问；管理员进行复盘提交时若没有教师档案，应要求提供教师 ID。

权限测试还需要验证 WebSocket 场景。WebSocket 连接建立时，后端从 query 参数或 Authorization Header 中解析 token，并加载用户上下文。后端按授权班级范围向普通教师广播状态数据，并在前端展示相应的座位、事件和运行状态，确保课堂画面和监控数据在授权范围内使用。

接口与权限测试是本系统的重要质量保证。课堂视频和学生行为记录属于敏感教学数据，系统通过统一 token 解析、用户上下文加载、班级权限查询和会话访问校验实现基本安全控制。真实环境部署可增加 HTTPS、访问日志脱敏、媒体短期票据和更细粒度的审计功能。

## 5.7 系统优化方向

系统优化方向包括：第一，扩大课堂行为标注数据集，补充不同机位、课程和光照条件下的样本，并定期开展模型训练。第二，结合姿态估计或时序动作识别方法，利用关键点和动作变化细化连续状态分析；多尺度特征与姿态线索可为连续状态建模提供参考[10-11]。第三，优化 SAHI 切片策略和模型推理方式，提高视频分析效率。第四，提供可配置的 VLM 复核服务，根据场景选用本地模型或云端模型。第五，完善教师复盘统计，按课堂时间段统计异常分布，按座位统计事件频次，生成课后报告。第六，完善隐私合规设计，明确数据保存周期、访问权限、脱敏策略和删除机制。

### 附录 D VLM 输出格式约束

```json
{
  "status": "",
  "label": "",
  "confidence": 0.0,
  "reason": ""
}
```

其中 `status` 使用 `NORMAL`、`HEAD_DOWN`、`DESK_LYING`、`TURNING_HEAD`、`EATING`、`UNCERTAIN` 或 `EMPTY` 等状态值。系统根据截图可见内容生成结果，异常结论使用“疑似”语气。
